# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Monorepo

**OpenCartable** — plateforme pédagogique libre (AGPLv3), auto-hébergée sur Raspberry Pi ARM64 : un prof authentifié compose des cours par blocs et les partage à ses élèves via des liens publics (les élèves n'ont pas de compte). L'utilisateur échange en **français**.

Trois répertoires, deux applications déployables :

- **[OpenCartableBack/](OpenCartableBack/)** — API FastAPI + SQLAlchemy 2.0 async + Alembic + PostgreSQL (asyncpg). Voir **[OpenCartableBack/CLAUDE.md](OpenCartableBack/CLAUDE.md)** pour les commandes, l'architecture et les décisions actées.
- **[OpenCartableFront/](OpenCartableFront/)** — SPA Angular 22 (zoneless, SSR + prerender), Transloco (fr/en), OIDC. Voir **[OpenCartableFront/CLAUDE.md](OpenCartableFront/CLAUDE.md)**.
- **[Assets/](Assets/)** — logos SVG (variantes mono/dark/horizontal) et documents de cadrage de référence (`Descriptions.md`, `DESIGN_SYSTEM.md`).

Chaque sous-projet est autonome (son propre `docker-compose.yml`, `Dockerfile`, `.git`-ignore, tests) et possède un **CLAUDE.md détaillé** : toujours lire celui du sous-projet concerné avant d'y travailler. Ce fichier-ci ne couvre que ce qui traverse les deux. Les dettes techniques acceptées « à terme » (ex. stratégie de purge des compteurs IA `ai_daily_usage`) sont suivies dans **[TODO.md](TODO.md)** — y ajouter toute nouvelle dette actée.

## Le contrat entre front et back

L'API et la SPA sont couplées par deux invariants transverses ; les casser côté d'un seul répertoire casse l'autre :

1. **La SPA est propriétaire du flow OIDC ; l'API est un resource server pur.** Le login (Authorization Code + PKCE vers Zitadel) est entièrement géré par le front ; l'API n'émet jamais de token et ne stocke aucune identité — elle valide le JWT de chaque requête. Corollaire côté back : `OIDC_AUDIENCE` doit correspondre au client id configuré côté front, et Zitadel doit émettre des **JWT access tokens** (pas les tokens opaques par défaut, sinon 401).

2. **Remplaçabilité de l'IdP confinée à un module de chaque côté** (exigence du cahier des charges) : back = `app/core/auth.py`, front = `AuthService` (`src/app/core/auth/`), seule couche autorisée à importer `angular-oauth2-oidc`. Ne jamais disperser de logique Zitadel ailleurs.

3. **Base d'URL API** : le front attaque `environment.apiUrl` (qui **inclut déjà `/api`**) ; le Bearer est attaché automatiquement par l'intercepteur OIDC à toute requête sous cette base. Côté back, les routes sont montées sous `settings.API_V1_PREFIX` (`/api/v1`). Route de référence du contrat de données : `GET /api/v1/subjects/tree`.

4. **Les liens publics élèves ne dépendent jamais de Zitadel.** Le régime d'accès élève (J2, livré) a sa propre autorisation des deux côtés : back = routes `/api/v1/public/*` **sans JWT** (visibilité du cours + token de partage vérifiés à chaque requête, `app/public/`) ; front = pages élèves sans Bearer (la `customUrlValidation` d'`app.config.ts` exclut `/v1/public/` de l'attachement du token — même un prof connecté consulte ces pages en anonyme).

## Cadrage produit et jalons

Le cahier des charges complet (architecture cible, modèle de données, roadmap J0→J5) fait foi et doit être mis à jour quand une décision d'archi change. **Attention : `Descriptions.md` et `DESIGN_SYSTEM.md` existent en plusieurs copies divergentes** (dans `Assets/`, `OpenCartableBack/`, `OpenCartableFront/`). Pour un travail back, se référer à `OpenCartableBack/Descriptions.md` ; pour un travail front/UI, à `OpenCartableFront/Descriptions.md` + `OpenCartableFront/DESIGN_SYSTEM.md`.

Côté front, dès la proposition, un **diff Monaco côte à côte remplace l'éditeur** (`app-proposal-review` — champ markdown masqué par classe, jamais `@if` : Monaco survit) avec commentaire + « Accepter et appliquer » (appliqué **via un édit Monaco entre undo stops** — **Ctrl-Z l'annule** comme une frappe — la propagation CVA alimentant l'autosave ; repli `setValue` sans undo si Monaco n'est pas prêt) / « Rejeter » (état `awaiting` + `pendingProposal`/`resumeProposal` de l'état de chat) ; le fil du chat ne porte qu'une carte informative. Le prompt d'édition dédié rend le bloc édité **en entier même en mode sommaire**, **déclare toutes les syntaxes du markdown de cours** (KaTeX, Mermaid, TikZ, GeoGebra, JSXGraph, `oc-resource:`/`oc-module:`) et le front **flush son autosave avant chaque tour** ; conversations rattachées au bloc (`block_id` — aucune migration, les CHECKs acceptaient déjà les 4 contextes), et l'état du chat front est extrait en **`AssistantChatState`** instanciable par hôte (le panneau flottant global — service root qui l'étend — et le chat ancré coexistent sur la page d'édition sans se marcher dessus) ; et la **troisième brique du J5 — le chat d'édition d'exercice (`block_exercise`), HITL par question** (décision actée : jamais un remplacement de l'exercice entier) : quatre tools de proposition — sujet, énoncé et/ou corrigé d'une question, ajout, suppression — une opération par appel, les questions du bloc édité désignées par des **références courtes `Q1…` stables le temps d'un tour** (numérotation capturée à l'interrupt et rejouée à la reprise, ids résolus ajoutés aux args à l'émission) ; côté back, les contextes d'édition sont des **descripteurs** (`app/course_assistant/editing/` — type de bloc, prompt, tools), le service et le flux SSE (extrait dans `streaming.py`) n'ont plus aucune branche par contexte ; côté front, `proposals.ts` parse les propositions par tool (union `AssistantPendingProposal`), `ProposalHost` orchestre les revues du block-editor — diff texte ou **revue structurée** `app-exercise-proposal-review` (carte par opération) sur les briques partagées `app-proposal-diff`/`app-proposal-decision` —, l'éditeur d'exercice applique l'opération (`applyStatement`/`applyQuestionEdit`/`applyQuestionAdd`/`applyQuestionDelete` — énoncés via Monaco, Ctrl-Z ; corrigé/ajout/suppression via le formulaire) et l'autosave est **flushée avant chaque décision**. ; et la **quatrième brique du J5 — le chat d'édition de module (`module`), HITL par fichier** (décision actée : jamais les trois fichiers d'un coup) : trois tools `propose_html_edit`/`propose_css_edit`/`propose_js_edit` (`new_code` intégral, plafond miroir de `MAX_CODE_LENGTH`, `rewrite_args` identité — pas de référence courte dans du code), la conversation pointant **`module_id`** (le descripteur `EditContext` gagne une **cible** `target` bloc|module, seul aiguillage hors descripteur — `_check_edit_target`/`_resolve_focus` —, aucune migration : les CHECKs acceptaient déjà `module`), le prompt substituant au catalogue markdown les **contraintes réelles du bac à sable** (`MODULE_RUNTIME`, miroir de `module-document.ts` : CSP sans réseau, storage inaccessible, bridge `ocModule.emit`) et le module édité rendu en entier ; côté front, `CourseChat` passe en modes `global | edit | placeholder` (le placeholder n'a plus d'hôte), `ProposalHost<V>` devient générique (`core/course-assistant/`) et les briques diff/décision migrent dans `shared/proposal/` ; dans `module-editor`, la revue `app-module-proposal-review` remplace le pane éditeur **pendant que l'aperçu sandbox exécute déjà le code proposé** (décision utilisateur), l'acceptation passant par Monaco pour les trois fichiers (Ctrl-Z complet). Restent du J5 : la résolution d'exercice élève (suivre le motif HITL acté — descripteur `editing/` côté back, genre de proposition + revue côté front), le **chat élève anonyme** (reporté — quota à imputer), les soumissions serveur et le RAG éventuel.

## Reverse proxy et infra

Le reverse proxy nginx (TLS, routage `/api` vers le back, protection SSRF SSR côté front) est fourni par l'infra, **hors de ce repo**. Les composes exposent l'API sur 8000 et le SSR sur 4000 sans proxy — c'est voulu.
