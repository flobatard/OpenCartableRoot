## 42. Pièces jointes des chats de l'assistant : une table à part, lues par un tool, jamais injectées (2026-09-24)

- Contexte : pour faire travailler l'assistant sur un document extérieur (photo d'un exercice de manuel, sujet PDF, barème `.docx`), le professeur n'avait que deux mauvaises options — recopier le contenu à la main, ou verser le fichier dans la bibliothèque du cours, que **le partage expose en entier à tous ses élèves** (décision 7) alors que ce n'est qu'un appui de travail. Trois contraintes cadraient la solution : l'API ne transporte pas de binaire (décision 3), le back ne traite pas d'image (décision 13), et le préfixe d'un tour doit rester cacheable (décision 23).
- Décision : une **table dédiée** `ai_attachments`, pas une `resource` — c'est ce qui garantit qu'une pièce jointe n'atteint **jamais** un élève, le régime public ne la connaissant pas. Upload par le flow presigné habituel (presign → PUT direct navigateur→S3 → confirm), sur le gabarit **strict de l'avatar** et non des ressources : whitelist de mimes **fermée**, plafond **par famille** (`image`, `pdf`, `text`, `office`), et confirmation qui re-vérifie au HEAD **taille ET `ContentType`** avant de purger l'objet hors gabarit — une URL présignée PUT ne borne rien. La pièce n'appartient d'abord qu'au couple (cours, propriétaire), `conversation_id` et `message_id` étant posés **à l'envoi du message** : c'est ce qui permet de joindre un fichier alors que la conversation est encore un brouillon sans id côté front. Le modèle, lui, ne reçoit **pas** le fichier : le contexte du tour l'**annonce** en référence courte (`A1`, `A2`…) avec nom, famille et taille, et un tool `read_attachment` le sert à la demande — décalque de `read_resource_pdf`/`read_resource_image`, dispatch sur la **famille** (une image est montrée en bloc multimodal, tout le reste rend du texte). Bureautique : `python-docx`, `python-pptx` et `odfpy` acceptés (l'extraction stdlib par `zipfile`+`ElementTree` a été écartée au profit de libs éprouvées), avec garde de taille décompressée et refus de `DOCTYPE` posés **en amont**, sans dépendre de la politique d'une lib tierce.
- Conséquences : **toute table qui écrit une clé S3 doit entrer dans les DEUX contrôles de cohérence** — l'anti-jointure de `reconcile_s3_orphans` (bucket → base ; sans la troisième, ajoutée ici, chaque pièce jointe serait déclarée orpheline et supprimée au bout de 90 jours, en silence tant que `PURGE_S3_ORPHANS_DRY_RUN` reste vrai) et la tranche à curseur de `missing_s3_objects` (base → bucket, dont le budget est désormais partagé entre les tables, avec un curseur par table). Second piège, plus insidieux : une conversation est rattachée à sa cible d'édition par une FK `CASCADE`, donc **supprimer un bloc, un module ou une ressource emporte des pièces jointes sans que personne ne purge leurs objets** — ce n'est pas un échec réseau occasionnel, que la réconciliation rattrape, mais un orphelin garanti à chaque suppression. D'où `app/course_assistant/queries.py`, que `app/courses/`, `app/modules/` et `app/resources/` appellent avant leur delete (un execute chacun, purge après commit) ; pour une ressource, la cascade va même deux niveaux plus loin (ressource → blocs `document` → leurs conversations → leurs pièces). Les références `A…` sont **stables à vie** dans une conversation (la liste ne fait que croître, triée `created_at, id`, et une pièce rattachée est **indélébile** — 409 à la suppression) : rien à capturer au registre HITL, contrairement aux `question_refs`, mais `_sse_resume` **doit** recharger les pièces jointes, `stream_agent` exigeant que le graphe d'une reprise expose les mêmes tools. L'instantané du flux devient un 4-uplet pour que les sous-assistants d'édition voient la pièce que le professeur vient de joindre au chat global. Le **contrat SSE est inchangé** (aucun événement ni champ nouveau) ; seul le détail de conversation gagne un execute et un champ additif. Une pièce jamais envoyée est du déchet, purgé par un dixième job (`ai_attachments`, rétention 7 jours). L'extraction bureautique est **dégradée et le dit au modèle** (en-tête explicite) : tableaux aplatis, mise en forme et images perdues. Le message garde un **texte obligatoire** : un `content` vide donnerait une bulle vide et un titre de conversation vide. Enfin, `python-pptx` fait entrer **Pillow** dans l'image — l'obstacle de la décision 13 tombe donc, sans qu'on s'en serve ici (le redimensionnement reste côté navigateur).
- Code : back `app/models/ai_attachment.py`, `app/course_assistant/attachments.py` (whitelist, plafonds, section du contexte), `office.py` (extraction + gardes), `tools.py` (`read_attachment`, `read_text_sync`, `read_office_sync`), `refs.py` (genre `attachment`), `context.py`, `prompts.py` (`ATTACHMENTS_RULE`), `service.py`, `router.py`, `schemas.py`, `streaming.py`, `queries.py` (collecte des clés avant cascade), `app/maintenance/service.py` (anti-jointure + `purge_unsent_attachments`), `registry.py`, `checks.py` (tranches à curseur par table), `app/courses/service.py` (`union_all` des clés), `app/courses/blocks.py`, `app/modules/service.py`, `app/resources/service.py`, migration `a3f1c7d94e20` ; front `core/course-assistant/attachment.model.ts`, `attachments.service.ts`, `image-downscale.ts`, `assistant-chat-state.ts`, `features/course-assistant/course-chat/course-chat-attachments.*`, `i18n/{fr,en}/courseChat.json`.

## 41. Journalisation de l'API : une seule dictConfig posée à l'import, un access-log maison et un id de corrélation par ContextVar (2026-09-21)

- Contexte : l'API n'avait **aucune** configuration de logging. Sous `uvicorn app.main:app`, seuls les loggers `uvicorn*` sont configurés et la racine reste sans handler : les 42 `logger.*` d'`app.*` du process API étaient donc **perdus** (les `warning`/`error` ne sortaient que par `logging.lastResort`, sur stderr, sans horodatage ni nom de logger) — dont le `logger.warning` de `app/starter_course/service.py` que sa propre docstring déclare « seul témoin en production d'un manifeste cassé ». Les deux entrypoints hors-API posaient chacun leur `logging.basicConfig`, **dupliqué mot pour mot**, avec le commentaire « l'API n'en a aucune ». Rien ne permettait de rattacher deux lignes à la même requête, ni de savoir ce qu'une requête avait coûté — sur un Pi mono-worker, la latence est le premier symptôme.
- Décision : un module unique `app/core/logging.py` (seul autorisé à configurer le logging, comme `core/kv.py` l'est pour redis), **sans aucune dépendance nouvelle** — stdlib `logging` + `contextvars`, `structlog`/`asgi-correlation-id`/OpenTelemetry écartés (contrainte ARM64, et rien de ce qu'ils apportent n'est utilisé ici). Format texte **aligné**, horodaté en **UTC ISO-8601** (tous les timestamps du projet le sont ; les conteneurs sont en UTC mais l'uvicorn de dev non — l'ambiguïté était un piège à diagnostic), avec une colonne d'id de corrélation à largeur fixe valant `-` hors requête. `configure_logging()` est appelée **au niveau module** de `app/main.py` : c'est le seul emplacement qui marche partout à la fois — uvicorn configure les logs dans `Config.__init__`, **avant** d'importer l'app, donc on reprend la main sans `--log-config` (qu'il aurait fallu répéter dans le Dockerfile, les deux composes, `launch.sh` et le README, sans couvrir ni les tests ni les process de maintenance) ; en `--reload` l'enfant reconfigure aussi avant d'importer. `disable_existing_loggers: False` est **non négociable** : `main.py` importe les 18 routeurs avant l'appel, leurs loggers existent déjà. La **racine reste à WARNING** et seul `app` suit `LOG_LEVEL` (à INFO, la racine allumerait `httpx` — une ligne par appel sortant vers Zitadel et vers le provider IA —, `botocore`, `apscheduler`, `langchain`) ; `uvicorn`/`uvicorn.error` perdent leurs handlers et propagent (leurs lignes passent par notre format), et **`uvicorn.access` est réduit au silence** au profit de notre ligne. L'access-log et la corrélation viennent d'un middleware **ASGI pur** monté en dernier (donc le plus externe) : `BaseHTTPMiddleware` rend la main dès `http.response.start`, on aurait mesuré le time-to-first-byte au lieu de la durée d'un flux SSE, et son `MemoryObjectStream` dans un task group séparé est la source historique des régressions de streaming. Id de **8 hexas** (`uuid4().hex[:8]`), lu dans un `X-Request-ID` entrant s'il est valide (`^[A-Za-z0-9_.:-]{1,64}$`) et **réfléchi** dans l'en-tête de réponse, `expose_headers` ouvert pour la SPA. Trois réglages seulement : `LOG_LEVEL`, `LOG_ACCESS`, `LOG_SLOW_REQUEST_MS`.
- Conséquences : la validation de l'id entrant n'est pas de la propreté mais de la **sûreté** — la valeur est réfléchie dans un en-tête (un CR/LF et h11 lève, soit un 500 offert au premier curieux) et écrite dans chaque ligne de log (fausse ligne de journal) ; même raison pour l'assainissement de la cible, `scope["path"]` étant percent-**décodé** par uvicorn comme par le TestClient (un `%0A` y injectait une ligne). Un `LOG_LEVEL` invalide retombe sur INFO avec un log au lieu de faire lever `dictConfig` à l'import — donc un conteneur en boucle de crash pour une faute de frappe dans un YAML (doctrine du cron de maintenance invalide). Le `?token=` des liens élèves est désormais **masqué** dans l'access-log de l'API (le nginx d'infra, lui, le voit toujours) : ça ne coûte aucune information de débogage et rend un extrait collable dans un ticket. Les réponses `text/event-stream` sont **hors** du seuil de lenteur : une génération IA dure une minute par nature. `/health` est journalisé en DEBUG plutôt qu'exclu (≈ 2880 appels/jour). `configure_logging()` ne doit **jamais** être appelée depuis `create_app()` : `dictConfig` vide les handlers de la racine, dont celui que pytest y pose pour `caplog` — un `make_client()` sous `caplog.at_level(...)` arracherait la capture. Un crash non rattrapé est journalisé avec sa durée mais sa réponse 500 ne porte pas l'en-tête, rendue par `ServerErrorMiddleware` en amont du nôtre (TODO.md) ; toute `HTTPException` ordinaire, elle, le porte. Chaque passe de job de maintenance reçoit son propre id (`correlation_scope` dans `run_job`), ce qui démêle enfin ses lignes de celles de la boucle de relève Redis qui tourne dans la même boucle asyncio. Contrepartie opérateur, la seule : **aucune rotation de logs dans les composes** (`json-file` sans `max-size`) alors que l'access-log augmente le volume sur la carte SD (TODO.md). Le `ContextVar` n'ajoute aucune contrainte : l'API est déjà mono-worker (décision sur le checkpointer HITL).
- Code : `app/core/logging.py` (`configure_logging`, `CorrelationIdFilter`, `UtcFormatter`, `correlation_scope`, `sanitize_correlation_id`, `AccessLogMiddleware`), `app/main.py` (appel au niveau module, montage après le CORS, `expose_headers`, log de démarrage du lifespan), `app/core/config.py` (`LOG_LEVEL`, `LOG_ACCESS`, `LOG_SLOW_REQUEST_MS`), `config/*.yaml` (documentés en commentaires), `app/maintenance/__main__.py` et `app/maintenance/scheduler.py` (le `basicConfig` dupliqué disparaît), `app/maintenance/runner.py` (`correlation_scope` dans `run_job`), `tests/test_logging.py`, `tests/test_access_log.py`.

## 40. Structure du cours par l'assistant global : propositions HITL sans sous-assistant, références de blocs renumérotées (2026-09-20)

- Contexte : l'édition globale (décision 36) ne savait que faire modifier une cible existante ; « ajoute un exercice après le cours », « supprime ce bloc », « mets les rappels en tête » restaient manuels (dette de TODO.md). Ces opérations ne produisent aucun contenu : un sous-assistant — son prompt, son catalogue de syntaxes, son thread — n'y apporterait rien. Elles heurtent en revanche un choix ancien : les références `B…` sont **positionnelles** (décision 9 — `B1` est le premier bloc affiché), donc tout changement de structure les décale.
- Décision : trois tools **bloquants** de plus sous `allow_edit`, `propose_block_add`, `propose_block_delete`, `propose_blocks_reorder`, qui sont des **propositions ordinaires** (`hitl_gate`, genre `proposal`) portées par le run de l'assistant global lui-même — `interrupt` sans `agent`, args réécrits à l'émission (ids résolus : `after_id`, `resource_id`, `module_id`, `block_id`, `block_ids`), reprise par la route de décision, que `allow_edit` retenu au registre autorise désormais hors contexte d'édition (en contexte `course` à édition globale, le seul genre `proposal` possible est structurel). Comme toute proposition, **le back n'écrit rien** : le front applique par les routes existantes du cours, puis décide. Un **ajout ne porte que la méta** (type, titre, description, position, ressource d'un `document`, module d'un `module`) : un bloc texte ou exercice est créé **vide** et l'assistant le fait remplir ensuite par `edit_block` — le prompt `course` reste sans catalogue de syntaxes ni protocole HITL, et le contenu reste revu en diff par le sous-assistant. Un **réordonnancement donne l'ordre complet** (contrat de `PUT /blocks/order` ; l'erreur liste inconnues, doublons et manquants). Les `B…` **restent positionnelles** : à la reprise, refs et tools sont rebâtis sur l'instantané rechargé, et le **résultat du tool rend le nouveau sommaire** (référence, titre, type) — avec, pour un ajout, la référence du bloc créé. Le registre capture pour cela la numérotation des blocs à l'interrupt (`block_refs`), qui n'est **jamais rejouée** (à l'inverse de `question_refs`) mais seulement comparée : bloc apparu (`new_block_refs`), référence d'origine d'un bloc disparu (`stale_blocks`/`block_gone`).
- Conséquences : le tool étant ré-exécuté à la reprise avec les args **d'origine** du modèle (jamais ceux réécrits), ses validations ne dépendent que de ce qui reste vrai après application — une suppression teste `block_gone` **avant** toute résolution (la référence positionnelle désigne désormais un autre bloc), une permutation complète le reste une fois renumérotée (l'identité est jugée sur les références, fonction des seuls args), et les textes d'acceptation ne citent jamais l'entrée résolue. La règle de prompt `STRUCTURE_RULE` dit au modèle de ne plus utiliser que les références du nouveau sommaire ; la garde des tools bloquants (décision 38) ne retient toujours qu'un appel bloquant par réponse, `edit_*` compris. Front : propositions **sans `delegation`** ni éditeur hôte — revue dans la fenêtre globale sur les blocs courants (détail chargé de `CourseService`, sinon `fetchDetail`, un GET qui ne touche pas aux signaux : `loadDetail` blanchirait la page cours), application **headless** (`addBlock` → ressource ou module pointé → `reorderBlocks` pour la position ; `deleteBlock` ; `reorderBlocks`), la page cours suivant par le signal `detail`. Une suppression est **refusée tant que l'éditeur du bloc est monté** (`TargetApplierRegistry` — son autosave écrirait dans le vide) et **toujours revue** en mode « Édition auto » (décision 27 : `ALWAYS_REVIEWED_KINDS`), ajout et réordonnancement étant réversibles à la main. Un ordre qui ne porte plus exactement les blocs du cours, ou un bloc visé disparu, ne laisse que le rejet. Limite assumée : l'ajout est une séquence de deux ou trois requêtes non atomique — interrompue, elle laisse un bloc en fin de cours, et « réessayer » en créerait un second (le professeur rejette et redemande).
- Code : back `app/course_assistant/structure.py`, `refs.py` (`block_refs`, `new_block_refs`, `stale_blocks`, `block_gone`), `hitl.py` (`PendingInterrupt.block_refs`), `streaming.py` (garde de `_sse_resume`, `_hitl_tools`, capture à l'interrupt), `tools.py` (`GLOBAL_EDIT_TOOLS`), `editing/base.py` (`ref_schema`), `prompts.py` (`STRUCTURE_RULE`), `tests/test_course_assistant_structure{,_api}.py` ; front `core/course-assistant/proposals.ts`, `course-assistant.service.ts`, `core/courses/structure-apply.ts`, `course.service.ts` (`fetchDetail`), `features/course-assistant/proposal-review/structure-proposal-review.*`, `global-proposal-review/`, `course-chat/course-chat.html`, `course-chat-tool.ts`, `i18n/{fr,en}/courseChat.json`.

## 39. Backoffice : un rôle de plateforme en base, des passes de maintenance demandées par l'API et exécutées par le scheduler (2026-09-18)

- Contexte : l'API n'avait aucune notion de rôle, l'état des jobs de maintenance (décision 37) ne se lisait qu'en `psql`, et un job en échec attendait sa prochaine occurrence — parfois une semaine. Un écran d'administration exige un rôle que l'IdP ne porte pas (les rôles applicatifs vivent en base, `Descriptions.md` §5.1 — l'IdP reste remplaçable, décision 1) et un moyen de lancer un job **sans l'exécuter dans uvicorn** (décisions 14 et 37), alors que rien ne reliait l'API au conteneur `scheduler`.
- Décision : un **rôle de plateforme** `users.platform_role` (`public` par défaut, `super_admin`), `String` + CHECK comme les autres énumérés et distinct des rôles pédagogiques `is_teacher`/`is_student`, exposé par `GET /users/me` et **jamais écrit par une route** (un utilisateur pourrait s'y promouvoir) : il se pose par la CLI `python -m app.users.roles grant|revoke|list` (compte désigné par `sub` ou email, email ambigu refusé). `get_current_user` ne touche toujours pas la base : la garde `require_super_admin` vit dans `app/users/` (résolution `sub → users`, puis rôle) et se pose au niveau du router `/admin`. Un compte sans le rôle reçoit un **403** — la doctrine « 404, jamais 403 » protège l'existence d'une *ressource* ; une route n'est pas un secret (le code est public), et 401 reste réservé au JWT. Pour lancer un job, **un Redis partagé sert de canal de contrôle** (service compose `redis`, sans persistance ; client confiné dans `app/core/kv.py`, protocole dans `app/maintenance/control.py`) : l'API dépose une demande `oc:maintenance:request:<job>` en `SET NX` (au plus une par job) avec une **expiration** (`MAINTENANCE_REQUEST_TTL_SECONDS`) ; le scheduler relève ces clés toutes les `MAINTENANCE_REQUEST_POLL_SECONDS`, **seulement quand aucune passe n'est en vol** (une demande n'attend jamais derrière le verrou), prend la plus ancienne en `GETDEL` (au plus une exécution par demande) et l'exécute par le `_execute` des crons — même verrou, même écriture d'état. En retour, il publie `oc:maintenance:status` (démarrage, fuseau, passe en cours et **son propre plan**, en UTC) à son démarrage puis au début et à la fin de chaque passe, et l'efface à l'arrêt propre. **Ni battement ni vérification de vie** : que le scheduler tourne est l'affaire de docker (restart, healthcheck, observabilité par-dessus). La boucle de relève est une **tâche asyncio**, pas un job APScheduler à intervalle (deux lignes INFO par exécution, et `get_jobs()` faussé).
- Conséquences : **rien ne touche Postgres périodiquement**. La base de preprod est un Neon managé qui se met en veille après quelques minutes sans requête ; une première version, qui passait par deux tables (une file relevée toutes les 10 s, une ligne de statut à battement), l'aurait tenue éveillée en permanence — ne jamais remettre de battement ni de relève en base, seules les passes elles-mêmes réveillent la base. Sans statut publié (scheduler arrêté proprement, pas encore démarré), l'API accepte quand même la demande, qui attend son démarrage dans la limite de son expiration ; seul un Redis injoignable fait refuser (503), la vue restant servie depuis Postgres (`control_available`). Redis étant sans persistance, un redémarrage perd demandes et statut ; le scheduler republie le statut au tour de relève suivant s'il le trouve absent. « En cours » existe pour toute passe du scheduler, cron ou demande ; le one-shot `python -m app.maintenance` reste hors verrou et invisible au backoffice (TODO.md). L'API importe le registre des jobs : alembic n'est plus importé qu'à l'appel de la garde de schéma, et l'API n'importe jamais `app.maintenance.scheduler` (APScheduler). Côté front, l'entrée « Administration » du menu utilisateur et `superAdminGuard` (fail-closed, à l'inverse d'`onboardingGuard`) ne font que masquer : le 403 est le barrage. Le profil étant en cache, une promotion ne se voit qu'après un rechargement.
- Code : back `app/models/user.py` (`platform_role`), `app/users/dependencies.py`, `app/users/roles.py`, `app/core/http.py` (`forbidden`), `app/core/kv.py`, `app/admin/`, `app/maintenance/control.py`, `app/maintenance/scheduler.py` (`consume_requests`, `poll_once`, `publish_status`, `_execute`), service `redis` de `docker-compose{,.preprod}.yml`, `tests/test_admin_api.py`, `tests/test_users_roles.py`, `tests/test_maintenance_control.py`, `tests/test_kv.py` ; front `core/users/super-admin.guard.ts`, `core/admin/`, `features/admin/`, `layout/header/user-menu.*`.

## 38. Garde des tools bloquants : la réponse du modèle élaguée avant l'état, plus de rejet à l'exécution (2026-09-18)

- Contexte : en édition globale (décision 36), le modèle lance volontiers plusieurs `edit_block`/`edit_module` dans une même réponse. La garde « un seul tool bloquant par réponse » (décision 34) agissait à l'**exécution** : le premier appel figeait le run, les suivants recevaient un `ToolMessage` d'erreur — mais ils étaient déjà entrés dans l'état, donc relayés au front (`tool_call` + `tool_result` en échec), persistés dans le tour, et renvoyés au modèle à chaque round suivant. Trois pollutions pour un comportement qu'on interdit de toute façon.
- Décision : la garde devient un `wrap_model_call` qui **élague la réponse du modèle avant qu'elle n'entre dans l'état** (`prune_blocking_calls`) : le premier appel bloquant par ordre est retenu, les appels non bloquants conservés, les autres appels bloquants retirés de `tool_calls` **et** de tout ce qu'un provider re-sérialise ensuite (blocs `tool_use` Anthropic, `function_call` Responses appariés par `call_id`, `tool_call` v1, copie brute `additional_kwargs["tool_calls"]`, `tool_call_chunks` d'un chunk agrégé) — l'historique renvoyé au modèle reste cohérent (chaque appel restant a son résultat). Le modèle ne voit au round suivant que l'appel retenu et son compte rendu, et renouvelle les autres un par un ; le prompt `DELEGATION_RULE` et les descriptions des tools `edit_*` le lui disent explicitement (un seul appel `edit_*` par réponse, les suivants ignorés).
- Conséquences : plus de résultat d'échec « appel ignoré » (ni sur le flux, ni en base, ni dans l'historique) ; le front n'a rien à changer. Un appel retiré est **perdu silencieusement** pour le modèle (c'est voulu : sa transcription ne le montre pas, il le rejoue s'il le veut encore). La règle reste déterministe et rejouée à la reprise, puisque c'est l'état checkpointé lui-même qui est élagué. L'appariement des blocs et copies se fait par id : un id partagé avec l'appel retenu (provider défaillant) n'est pas retiré du contenu.
- Code : `app/core/ai/agent.py` (`prune_blocking_calls`, `_blocking_guard_middleware`, `_TOOL_CALL_BLOCK_TYPES`), `app/course_assistant/prompts.py` (`DELEGATION_RULE`), `app/course_assistant/delegation.py` (descriptions des specs), `tests/test_ai_agent.py`.

## 37. Maintenance : un scheduler APScheduler résident, une cadence par tâche, un état en table (2026-09-18)

- Contexte : la boucle shell du service `purge` (décision 14) lançait les sept tâches **d'un bloc** toutes les `PURGE_INTERVAL_SECONDS`, à une heure qui dérivait au gré des redémarrages — sur un Pi, l'`UPDATE` des tours d'outil (seq scan et réécriture TOAST sur `ai_messages`) et le balayage intégral du bucket tombaient donc ensemble, parfois en pleine journée. Aucune cadence par tâche n'était exprimable, et la seule trace d'une passe était un log qui tourne : rien ne disait si la purge de la semaine avait eu lieu, ni ce qu'elle avait touché.
- Décision : le service compose devient **`scheduler`** (`python -m app.maintenance.scheduler`, entrypoint toujours écrasé — les migrations restent le job du seul `api`), un **`AsyncIOScheduler` résident** qui planifie chaque job individuellement par une **expression cron lue dans `config/*.yaml`** (`MAINTENANCE_CRON_*`, défauts en dur dans `Settings` : purges légères quotidiennes vers 03 h, les deux jobs au coût non borné une nuit de week-end **chacun la sienne**), avec `coalesce`, `max_instances=1`, `misfire_grace_time` et un verrou global — **pas de rattrapage**, une occurrence manquée est sautée puisque les tâches sont idempotentes. `PURGE_INTERVAL_SECONDS` disparaît. Le registre `registry.py` est la **seule** liste de jobs (nom **anglais**, libellé français pour les logs, cadence, rétention, besoin de `Storage`) et `runner.py` donne au scheduler et au one-shot `python -m app.maintenance [job…]` exactement la même sémantique. Chaque passe **upserte une ligne** dans `maintenance_job_state` (PK = nom du job, bornée par construction donc jamais purgée : statut, compte, durée, erreur tronquée, échecs consécutifs, total, détail JSONB), écrite sur une **session dédiée** — celle du job peut être transactionnellement morte au moment précis où son échec doit être enregistré. Deux **contrôles en lecture seule** s'ajoutent, qui observent sans jamais corriger : `storage_inventory` (lignes par table, octets sur disque, objets et octets par préfixe S3) et `missing_s3_objects` (cohérence **inverse** de la réconciliation — lignes `available` pointant un objet absent, HEAD à concurrence bornée, plafond de clés par passe et **curseur tournant** mémorisé dans `last_detail`).
- Conséquences : le conteneur héberge désormais un **process Python résident** (~60 Mo contre ~1 Mo pour `sh`+`sleep`) — c'est le prix assumé d'une cadence par tâche et d'un état en base. Il installe son **propre handler SIGTERM** (le noyau ne délivre pas à PID 1 un signal dont le handler est celui par défaut : sans lui, `docker stop` attendrait dix secondes puis SIGKILL, à chaque déploiement), et l'arrêt **n'utilise pas `shutdown(wait=True)`**, qui *annule* les jobs au lieu de les attendre dans `AsyncIOExecutor` — les passes en vol sont tenues derrière un `asyncio.shield` puis drainées. Deux **leviers d'inactivité** coexistent et ne doivent jamais être confondus : **rétention 0 = tâche désactivée** (le job reste planifié et sort en `skipped`) et **cron vide ou invalide = job non planifié** (aucune ligne d'état ; une expression fautive n'empêche jamais le démarrage, seul son job est perdu). Les crons sont en **heure locale** (`MAINTENANCE_TIMEZONE`, repli sur UTC journalisé et vérifiable dans la ligne de boot) : le jour de semaine s'écrit **en lettres** (`CronTrigger.from_crontab` indexe 0 = lundi, pas dimanche comme crontab) et **aucune occurrence ne tombe entre 02:00 et 02:59** (heure inexistante au passage à l'heure d'été, doublée à l'automne) — deux tests le garantissent sur toute la table. La raison d'un `skipped` va dans `last_error`, jamais dans `last_detail`, qui ne doit pas perdre son curseur ; `consecutive_failures` n'est pas touché par un saut. Plus de passe au démarrage : le boot **journalise le plan** (cadence et prochaine occurrence de chaque job) et `docker compose exec scheduler python -m app.maintenance` remplace l'ancienne vérification immédiate. L'ordre des `execute` de `run_job` (garde de schéma, puis détail précédent, puis la tâche) est un contrat testé. `pool_recycle=1800` est posé sur l'engine partagé : un process résident dont les jobs sont espacés de plusieurs heures ne doit pas payer un timeout TCP sur une connexion blackholée.

## 36. Édition globale du cours par délégation à des sous-assistants d'édition (2026-09-17)

- Contexte : le panneau flottant (contexte `course`) était en lecture seule — explorer, critiquer, synthétiser — et toute modification passait par le chat ancré d'un éditeur, une cible à la fois, le professeur ouvrant chaque éditeur lui-même. Une demande transversale (« harmonise les introductions », « ajoute une question d'application à chaque exercice ») restait manuelle. Les descripteurs d'édition (décisions 10, 11, 34) savaient déjà tout faire sur une cible ; il manquait un orchestrateur, et une revue qui ne dépende plus de l'éditeur monté.
- Décision : l'assistant global **ne modifie jamais lui-même**. Quand le professeur active l'**édition globale** (interrupteur du pied du panneau, préférence du navigateur `oc-assistant-global-edit` envoyée à chaque tour dans `allow_edit` — jamais persistée côté compte, comme le mode auto), il reçoit deux tools **bloquants**, `edit_block` (bloc texte ou exercice) et `edit_module`, qui confient UNE cible et des **consignes autonomes** à un **sous-assistant d'édition** : un run agent à part entière bâti sur le descripteur existant de la cible (son prompt, ses tools de proposition, sa gate HITL, ses réécritures), sur son **propre thread**. Orchestration **hors du graphe**, dans le driver du flux SSE (`_drive_turn`) : le tool `edit_*` fige le parent d'un interrupt de genre `delegation` — jamais relayé au front, jamais enregistré au registre — et le driver lance le sous-assistant dans le même flux, ses événements tagués `agent` (champ SSE additif sur `token`, `thinking`, `tool_call`, `tool_result`, `interrupt`). Une proposition ou des questions du sous-assistant suivent le flux HITL ordinaire — `interrupt` porteur d'`agent`, entrée de registre à `delegation` (thread du sous-assistant, parent figé derrière, décisions déjà rendues, compte de délégations) — et les routes de décision et de réponse reprennent SON run ; quand il termine, son **compte rendu** (propositions tranchées, message final abrégé) est la valeur de reprise du parent, donc le résultat du tool, et l'assistant continue (peut redéléguer, puis répond). Un sous-assistant à la fois : le parent est figé pendant toute sa durée et la garde des tools bloquants ne retient qu'un `edit_*` (ou `ask_questions`) par réponse (décision 38) ; plafond de 10 délégations par tour (le `run_limit` du graphe repart à chaque reprise : il ne les borne pas) — atteint, le tour se clôt sur une notice et le run parent est abandonné. Le prompt du contexte `course` a désormais **deux variantes statiques** (avec ou sans la règle de délégation), toujours sans catalogue de syntaxes ni protocole HITL, réservés aux sous-assistants. Front : la proposition d'un sous-assistant arrive dans le panneau global rattachée à sa délégation (cible, contexte, titre — args de l'appel `edit_*` réécrits par le back) et se revoit dans une **fenêtre `<dialog>` globale** hébergée par l'outlet **à côté** du panneau (visible sur toute page du cours, éditeur mobile compris) ; l'acceptation l'applique **sur la cible** avant la décision — via l'éditeur s'il est monté (`TargetApplierRegistry` : Monaco, Ctrl-Z, flush d'autosave), sinon par un **PATCH headless** (`CourseService`, `ModuleService`, qui patchent leurs signaux : la page cours suit) ; le mode « Édition auto » (décision 27, révisée) vaut aussi pour ces propositions.
- Conséquences : `PendingInterrupt` gagne `allow_edit` (rejoué à la reprise : mêmes tools, même prompt qu'à l'aller) et `delegation` ; une entrée à `delegation` tient **deux threads**, purgés ensemble (abandon, suppression, expiration, fermeture du flux) ; l'usage d'un flux sans ligne à persister (sous-assistant seul) est reporté sur le segment suivant par le registre (`carried_usage`). La **transcription du sous-assistant n'est pas persistée** (v1) : seuls l'appel `edit_*` (args réécrits) et son résultat le sont — après rechargement, la carte de délégation garde cible, consignes et compte rendu, mais une proposition de sous-assistant en attente n'est pas ré-offerte (TODO.md). `encode_turn` tague les événements (`agent`) et absorbe un `done` intermédiaire (`None`) ; `_AssistantTurn` a un mode agent (rien de persisté, compte rendu composé des décisions). Aucun rechargement d'instantané dans un flux (contrats FIFO inchangés) : toute édition acceptée passe par une route de décision, qui recharge. `ProposalHost.apply` peut être asynchrone (erreur `apply` sur un PATCH refusé, réessayable) ; le repli du tour live ignore l'activité `agent` ; l'« original » de la revue globale est figé par proposition (un PATCH en mode auto ne vide pas le diff du repli) et l'application en mode auto attend la cible en vol. Les questions d'un sous-assistant s'affichent dans le panneau global — effacé sous 900 px sur un éditeur (TODO.md). La création, la suppression et le déplacement de blocs sont venus ensuite, sans sous-assistant (décision 40). Mesure : `assistant_message_sent` gagne `allowEdit`, `assistant_global_edit_changed` compte les bascules ; `.global-proposal-review` est masqué des replays.

## 35. Colonnes du markdown de cours : conteneur `::: columns` / `+++` / `:::`, empilement selon la largeur disponible (2026-09-17)

- Contexte : le contenu d'un bloc se lisait strictement de haut en bas, alors qu'un support de cours met souvent deux contenus en regard — une définition et son exemple, une figure et son explication, un programme et son commentaire, une formule et le module qui la fait vivre. Tout ce qu'on veut y placer (images `oc-resource:`, modules `oc-module:`, code exécutable, encadrés, formules, figures) vit déjà dans le markdown. Placer deux blocs côte à côte aurait en revanche demandé un modèle en base, une migration et des changements dans l'éditeur, la navigation élève, l'export/import et l'assistant, pour un gain limité (un PDF embarqué ou un exercice en colonne).
- Décision : un **conteneur dans le markdown** (§5.3 : le markdown couvre la mise en forme, sans type de bloc dédié), à la manière des divs Pandoc — `::: columns` (ou `::: columns 1:2` / `::: columns 2:1` : un tiers et deux tiers), le markdown de la colonne de gauche, `+++`, celui de la colonne de droite, `:::`. `+++` parce qu'il ne signifie rien en CommonMark, là où `---` serait une règle ou un titre setext. Chaque marqueur est seul sur sa ligne (au plus 3 espaces d'indentation ; casse et longueur des marqueurs tolérées), il faut exactement un `+++` au niveau du conteneur, les blocs de code sont opaques et tout `:::` suivi de texte ouvre un niveau ; un conteneur mal formé reste du texte, marqueurs visibles. Rendu par une **extension de bloc marked** (`courseColumns`) qui relexe chaque colonne : tout le pipeline s'applique à l'intérieur (encadrés, KaTeX, Mermaid, extensions, ressources, modules). **Empilement intrinsèque** : `flex-wrap`, `flex-basis: 0` et largeurs minimales proportionnelles au ratio, donc un seuil unique de 26em de largeur disponible — calé sous la plus étroite des largeurs de lecture, 54ch en serif (27em) —, sans aucune requête de largeur : le même markdown se lit dans l'aperçu d'un éditeur, le chat de l'assistant ou un bac à sable de doc, plus étroits que le viewport. Un bouton « Insérer des colonnes » sous l'éditeur markdown pose le squelette, la sélection devenant la colonne de gauche.
- Conséquences : les marqueurs et les ratios sont un **contrat de contenu** — on en ajoute, on n'en retire ni n'en renomme ; seule la graphie canonique `::: columns` est enseignée (aide de l'éditeur, page de doc `columns`, catalogue `MARKDOWN_SYNTAXES` des contextes bloc texte et exercice, cours d'exemple gardé par un scanner miroir de `splitColumns`). Aucun changement de schéma, d'API, d'export/import ni de recherche : les références `oc-*` sont réécrites par regex partout dans le markdown. Un ouvrant collé sous une citation, une liste ou un tableau est absorbé par eux (continuation paresseuse) : une ligne vide est nécessaire, et le bouton l'insère. Le hint `start` de marked est ancré sur `\n` et non validé (un conteneur non fermé ne coûte pas un parcours par paragraphe) ; chaque colonne est relexée en restaurant `lexer.state.top`, qu'une liste serrée tient à false. À l'impression, les colonnes restent côte à côte et insécables quand elles tiennent sur la page ; comme pour un encadré, un conteneur plus haut qu'une page part d'abord sur la page suivante. L'export HTML n'a rien de spécifique (CSSOM vivant). Hors d'OpenCartable (GitHub, export markdown), les marqueurs restent des lignes lisibles. `MarkdownEditor` gagne `replaceSelection` (une étape d'annulation, texte de remplissage sélectionné), auquel `insertAtCursor` délègue désormais ; `MarkdownPlayground` gagne `stacked`, sans quoi son aperçu de 24em empilerait toujours les colonnes. La dette « formule KaTeX en ligne non sécable » vaut aussi dans une colonne étroite (TODO.md).

## 34. Questions de l'assistant au professeur : tool HITL `ask_questions`, formulaire à la place du composer (2026-09-13)

- Contexte : face à une demande ambiguë (« crée un exercice »), l'assistant ne pouvait que deviner ou poser sa question en prose — le prof retapait sa réponse au tour suivant, et les choix structurants (niveau, notions, format) se perdaient dans le fil. Le seul HITL existant, la proposition d'édition (décisions 10, 11, 27), n'existait que dans les contextes d'édition et figeait le run pour un clic Accepter/Rejeter, pas pour une réponse.
- Décision : un tool **bloquant** `ask_questions`, exposé dans les **quatre contextes** de l'assistant (panneau global compris, jamais le tuteur élève) : 1 à 4 questions dans UN appel, chacune à choix unique ou multiple avec 2 à 6 suggestions en texte brut (libellé + précision facultative), un choix libre **« Autre » toujours ajouté par l'interface** (une suggestion « Autre » est refusée à la validation). Même mécanique que les propositions — le run est figé par `interrupt`, les questions voyagent dans les `args` du `tool_call`, la reprise ré-exécute le tool dont le résultat EST la réponse — mais une route à part, `POST …/conversations/{id}/questions/{tool_call_id}/answer` (`{declined, answers: [{selected: [index], other}]}`), et un genre (`kind`) porté par l'interrupt (champ SSE additif) et par le registre : une décision ne reprend jamais des questions, ni l'inverse. Front : les questions remplacent le **composer** du chat, **une par étape** (Précédent / Suivant / Répondre), **toutes obligatoires** (une suggestion ou un texte « Autre » non vide) ; la **croix** est le seul refus, pour toute la série, et l'IA poursuit alors avec des hypothèses signalées, sans reposer les questions. Le chat replié se déplie à l'arrivée d'une série. Les questions restées sans réponse en fin de conversation sont **reproposées à sa réouverture** (le back garde la reprise jusqu'à son TTL ; un 404 à la réponse = expirées, notice et retour du composer) — les propositions, elles, ne le sont toujours pas.
- Conséquences : **tout tour d'assistant est checkpointé** (`thread_id` même en contexte `course`) ; pour borner la mémoire sur le Pi, l'état n'est écrit qu'à la sortie du graphe (`durability="exit"`, suffisant pour une reprise), et le thread est purgé à `done`, à l'erreur, à la **fermeture d'un flux resté sans suite** (Stop, déconnexion — fuite qui existait déjà pour les contextes d'édition), à la **suppression de la conversation** et au **balayage des reprises expirées** (`hitl.sweep_expired`). Deux interrupts dans une même réponse du modèle rendaient la reprise impossible (`RuntimeError` LangGraph, un 503) et un modèle qui pose ses questions en appels parallèles le déclencherait : `AIToolSpec.blocking` et une **garde déterministe** dans `app/core/ai/agent.py` n'exécutent que le premier appel bloquant de chaque réponse, les suivants reçoivent un résultat d'échec — même décision à la reprise. `hitl.suspend` devient le **seul appelant** d'`agent_interrupt` (`hitl_gate` y délègue). La route contrôle la réponse contre la forme retenue au registre **avant** de consommer la reprise (422 réessayable). Replay : un round dont un appel est sans résultat est replié en texte (un `tool_call` non apparié ferait un 400 provider), les réponses du professeur ne sont jamais abrégées. Prompt : règle `QUESTIONS_RULE` dans les règles communes de l'assistant (cache de prompt manqué une fois au déploiement). La carte du fil affiche le texte du résultat (questions et choix, ou refus) ; la mesure ne compte que des nombres (`assistant_questions_answered`) et le formulaire est masqué des replays. Le tuteur n'a pas l'outil (aucun run checkpointé, un tour = une ligne à verdict — TODO.md).

## 31. Encadrés pédagogiques en syntaxe d'alerte GitHub, dans le pipeline markdown (2026-09-11)

- Contexte : les supports de cours de toutes les matières mettent en valeur définitions, méthodes, points à retenir et mises en garde. Un fence ne convient pas — son contenu est du texte brut, alors qu'un encadré contient formules, listes et figures — et un type de bloc dédié casserait le fil du texte (décision de §5.3 : le markdown couvre les encadrés).
- Décision : la syntaxe des **alertes GitHub**, déjà connue des modèles et des profs qui écrivent du markdown, rendue par le pipeline synchrone : une citation dont la première ligne commence par `[!TYPE]` devient un encadré, le reste de cette ligne est un titre personnalisé (à la manière d'Obsidian), le contenu est du markdown complet. Six types scolaires dont les mots-clés **canoniques sont les types eux-mêmes, en anglais comme toute clé du code** — `DEFINITION`, `KEYPOINT`, `METHOD`, `EXAMPLE`, `NOTE`, `WARNING`, qui nomment aussi les classes CSS et les clés i18n (*révisé le 2026-09-12* : la syntaxe était d'abord en mots-clés français, seul identifiant français du contrat de contenu, et `KEYPOINT` n'existait pas). Alias reconnus pour toujours : les mots-clés français d'origine (`RETENIR`, `A RETENIR`, `METHODE`, `EXEMPLE`, `REMARQUE`, `ATTENTION`) et ceux des alertes GitHub sans graphie canonique (`TIP`, `IMPORTANT`, `CAUTION`) ; casse, accents et espaces indifférents. Titre par défaut dans la **langue de l'interface** (comme « av. J.-C. » des frises), passé au rendu par `markdown-view`. Type inconnu : la citation reste une citation, marqueur visible.

Seule la graphie canonique est enseignée : pages d'aide et de doc, `MARKDOWN_SYNTAXES` du back, cours d'exemple (garde `_CALLOUT_CANONICAL`). Le titre par défaut dépend de la langue : il entre dans la clé du gel de rendu de `markdown-view`. Hors d'OpenCartable (export markdown, GitHub), un encadré reste une alerte ou une citation lisible.

## 30. Librairies préinstallées dans le bac à sable des modules, inlinées par le runtime (2026-09-11)

- Contexte : la décision 4 coupe tout réseau aux modules (CSP `default-src 'none'` du srcdoc) : aucun CDN, donc « JavaScript natif écrit à la main ». Les simulations de physique ou de SVT, les graphiques et la 3D restent alors hors de portée de l'assistant comme du prof, et coller une librairie dans le JS stocké est impossible (200 000 caractères par champ, code renvoyé en entier au modèle à chaque tour).
- Décision : six librairies **servies par l'app** et déclarées par un **pragma** en commentaire dans le JS du module, `// @oc-libs: matter, chart` — `matter` (Matter.js 0.20), `chart` (Chart.js 4), `p5` (p5.js **2.x**), `jsxgraph` (JSXGraph 1.x, CSS comprise), `d3` (D3 7), `three` (Three.js, OrbitControls inclus). Le **parent** (origine de l'app) lit leur texte sous `/assets/module-libs/` (préparé au postinstall par `scripts/prepare-module-libs.mjs` : UMD copiés, Three bundlé en IIFE par esbuild, noms de fichiers stables, garde contre `</script`/`<!--`) et l'**inline** dans le srcdoc, entre le bridge et le JS du prof. La **CSP n'est pas rouverte** : `script-src 'unsafe-inline'` couvre ces scripts, l'iframe ne fait aucune requête. Pas de schéma, de colonne ni d'outil IA : le pragma voyage avec le JS (export, import, propositions `propose_js_edit`), un nom inconnu est ignoré (et signalé dans l'éditeur). Pragma plutôt qu'injection systématique : p5 pèse ~1 Mo et son « mode global » s'active dès qu'un module définit `setup`/`draw`.
- Conséquences : composition **asynchrone** quand un pragma est présent (`ModuleLibraryLoader`, cache mémoire par fichier, échec retiré du cache), gardée par un compteur de génération dans `ModuleRunner` ; sans pragma, le chemin synchrone est inchangé. Chaque iframe re-parse sa librairie (pas de cache HTTP du module lui-même — TODO.md). Le catalogue est un **miroir** : `MODULE_LIBRARIES` (front) = `MODULE_LIBRARY_NAMES` et la puce « Bibliothèques » de `MODULE_RUNTIME` (back), qui documente aussi les pièges (dimensionner sur la largeur à cause de l'auto-resize, p5 2.x sans `preload`, aucun chargement par URL). p5 et JSXGraph sont LGPL, servis non modifiés avec leur licence. Le cours d'exemple montre une librairie par module, gardé par des tests (pragmas au catalogue, usage de chaque librairie déclarée, catalogue entièrement couvert).
- Code : front `shared/module-runner/` (`module-libraries.ts`, `module-library-loader.ts`, `module-document.ts`, `module-runner.*`), `features/courses/module-editor/`, `scripts/prepare-module-libs.mjs`, `angular.json` (assets), `src/static-headers.ts` ; back `app/course_assistant/prompts.py`, `app/starter_course/manifest.json`, `tests/test_starter_course.py`.

## 29. Code exécutable côté élève (SQL, Python) : runtimes WASM en Worker, chargés au clic (2026-09-11)

- Contexte : NSI, maths et physique au lycée demandent du code qui tourne — des requêtes SQL, des scripts Python. Un serveur d'exécution est exclu (Raspberry Pi, élèves sans compte, sécurité) : le code doit s'exécuter dans le navigateur de l'élève, en WebAssembly. Mais les runtimes pèsent lourd (sql.js ~0,7 Mo, Pyodide ~13 Mo), un code d'élève peut boucler sans fin, et du code exécuté sur l'origine de l'application ne doit ni lire ses jetons ni contacter un tiers.
- Décision : les fences ```` ```sql ```` et ```` ```python ```` deviennent exécutables (bouton Exécuter, code modifiable par l'élève, sortie sous le code) via une brique commune `RunnableCode`. Le runtime est servi **depuis l'origine** (`/assets/sqljs/`, `/assets/pyodide/`, copiés par `angular.json`, jamais bundlés), téléchargé au **premier clic** — jamais à l'affichage —, tenu par un **service root** et exécuté dans un **Worker** résiliable : délai (5 s par requête SQL), bouton Arrêter, worker tué puis recréé à la demande. Le serveur SSR pose une **CSP d'en-tête sur les scripts de worker** (`default-src 'none'; script-src 'self' 'wasm-unsafe-eval'; connect-src 'self'` — la CSP d'un worker vient de son script, pas du document) et `Cache-Control: no-cache` sur les runtimes non hashés. SQL : sql.js dans son propre worker classique, base neuve à chaque exécution (préparation avant `-- @query`, puis la requête). Python : Pyodide 314 dans un worker **module** bundlé par Angular (Pyodide chargé à l'exécution depuis `/assets/pyodide/`), avec numpy et matplotlib : leurs 12 wheels sont téléchargées au postinstall depuis la distribution officielle de la même version et **vérifiées par sha256**, et le lock servi est **élagué** aux paquets hébergés (tout autre import lève `ModuleNotFoundError`) ; `MPLBACKEND=Agg`, figures sérialisées en PNG en fin d'exécution, délai de 15 s armé une fois Python et les paquets chargés.
- Conséquences : un Worker n'a ni DOM ni stockage (aucun accès aux jetons OIDC) et, en production, ne peut joindre que l'origine ; `ng serve` ne pose pas ces en-têtes (vérification sous `serve:ssr`). Si nginx ajoute sa propre CSP, elle se cumule à celle du worker et doit autoriser `'wasm-unsafe-eval'` (TODO.md). Les blocs sont indépendants (aucun état partagé entre deux exécutions) ; les exécutions d'une page sont sérialisées sur un seul worker. Les fences ```` ```sql ```` existants et ceux écrits par l'assistant, chat compris, deviennent exécutables — voulu. Le manifeste du cours d'exemple est gardé par une **vraie exécution** dans `sqlite3` et par la compilation des programmes Python (imports limités aux paquets hébergés) pendant pytest. Vérifié en navigateur sous la CSP de production : Pyodide, numpy et matplotlib se chargent, et un `fetch` Python vers une autre origine échoue (il passe sous `ng serve`, sans l'en-tête). `npm install` a besoin du réseau pour les wheels (`OC_SKIP_PYODIDE_PACKAGES=1` pour s'en passer) ; Pyodide exige Chrome 112, Firefox 114 ou Safari 16.4.
- Code : front `shared/markdown-extensions/runnable-code/`, `shared/markdown-extensions/sql/` (`sql-runtime.ts`, `sql-config.ts`, `sql-view.ts`), `shared/markdown-extensions/python/` (`python.worker.ts`, `python-runtime.ts`, `python-output.ts`, `python-view.ts`), `scripts/prepare-pyodide.mjs`, `src/static-headers.ts`, `src/server.ts`, `angular.json` (assets), `.dockerignore` ; back `app/course_assistant/prompts.py`, `tests/test_starter_course.py`.

## 28. Graphiques Vega-Lite rendus en SVG statique durci (2026-09-11)

- Contexte : les graphiques de données (mesures de TP, climatogrammes, données démographiques) manquaient au markdown de cours. Vega-Lite est une grammaire JSON que les modèles connaissent bien et qui produit du SVG (donc imprimable), mais Vega compile par défaut ses expressions en `new Function`, sait charger des données (`data.url`), des images et suivre des liens : un contenu de cours pourrait faire partir des requêtes du navigateur de chaque élève vers un tiers, et exigerait `'unsafe-eval'` sous une CSP stricte.
- Décision : fence ```` ```vegalite ```` rendu **statique et hermétique**. La spec est refusée si elle porte une clé `url` à n'importe quel niveau (données en ligne `data.values` seulement, message explicite) ; les expressions passent par `vega-interpreter` (`parse(…, {ast: true})`), jamais par `new Function` ; le loader rejette tout `load` et tout `sanitize` (aucune requête, aucun `href`) ; la vue tourne sans renderer et `toSVG()` produit un SVG texte re-sanitisé par DOMPurify, posé sur la planche claire fixe `--figure-board`. Pas de `vega-embed` (menu d'actions et thèmes inutiles).
- Conséquences : aucune interactivité (info-bulles, sélections — TODO.md) ; couleurs du thème Vega figées, d'où la planche claire ; ~250 ko gzip de chunks paresseux payés seulement par une page qui affiche un graphique ; les `id` des clips et dégradés du SVG sont rendus uniques à l'impression (`uniquifySvgIds`). Le catalogue de l'assistant (`MARKDOWN_SYNTAXES`) rappelle « jamais d'url » et le manifeste du cours d'exemple est gardé par un test.

L'éditeur n'est plus masqué sur `pending()` mais sur `review()`. ## 26. Mesure d'audience PostHog en opt-in strict, URLs nettoyées avant envoi (2026-09-10)

- Contexte : le projet n'avait **aucune mesure d'audience** et **aucun cookie** (décision 21), donc aucune idée de ce que ses utilisateurs font — combien de profs créent un cours, combien de liens partagés sont réellement ouverts, si le tuteur sert. Deux contraintes propres à OpenCartable interdisaient de brancher un SDK tel quel : le public inclut des **élèves mineurs sur des pages publiques anonymes**, et le **token de partage est un segment d'URL** (`/:lang/shared/<token>/…`, décision 6) — une capability URL, que `$current_url` aurait expédiée à PostHog à chaque événement, donnant à quiconque lit le dashboard l'accès en clair aux cours partagés. Même problème avec `?q=` de `/search`, et avec le titre du document, que `SeoService` renseigne avec le titre du cours consulté.
- Décision : mesure **par environnement** (`environment.analytics` : `enabled`, `posthogKey`, `posthogHost`, `sessionReplay` — garde dure `enabled && posthogKey non vide`, sinon **inerte**) et **opt-in strict** : posthog-js n'est même pas **téléchargé** avant consentement (`await import('posthog-js')`, jamais d'import statique — le bundle initial est budgété à 1 Mo et un déploiement qui ne mesure rien ne doit rien payer). Le consentement vit dans un service **indépendant de PostHog** (`core/consent/`, clé `oc-consent`, version + péremption à 6 mois, refus persisté aussi longtemps qu'un accord), lu **après hydratation** (`afterNextRender`) parce que la home et la page de confidentialité sont prerendues. Tout ce qui sort passe par `scrubEvent` posé en `before_send` : query et fragment supprimés, segment après `shared` réécrit `:token`, UUID réécrits `:id`, titre du document retiré — PostHog ne voit que des **motifs de route**. Sous consentement, la **mesure est large et assumée** : `autocapture`, clics de rage, clics morts, cartes de chaleur, performances de chargement, exceptions JS, vues de page par `history_change`, plus les événements explicites de la carte typée `analytics.events.ts` ; seuls les sondages sont coupés. `person_profiles: 'always'` (un profil de visiteur pour tous, élèves anonymes compris) et `persistence: 'localStorage+cookie'` — la décision 21 porte sur l'**API** (Bearer, `allow_credentials: false`) et n'interdit rien au front ; le cookie reste sur l'hôte exact (`cross_subdomain_cookie: false`, l'API vit sur un sous-domaine frère) et `secure_cookie` suit `production`. **`//flags` n'est jamais coupé** : replay, cartes de chaleur et autocapture y lisent leur configuration distante — `advanced_disable_flags: true` rendrait `startSessionRecording()` silencieux. Replay désactivé par défaut, **jamais sur une page élève** (il filmerait des réponses de mineurs), `maskAllInputs` partout et `maskTextSelector` sur les sorties du modèle et les corrigés (`REPLAY_MASK_SELECTOR`). Un prof connecté est identifié par son **`sub` OIDC seul**, jamais son email ni son nom. Règle d'or des propriétés **des événements explicites** : un **énuméré ou un compteur**, jamais de contenu, de saisie ni d'identifiant (l'autocapture, elle, enregistre le libellé de l'élément cliqué — assumé et écrit dans la page de confidentialité). Bannière non modale montée dans le shell (donc sur les pages élèves aussi) mais **derrière un `@defer`** — un visiteur qui a déjà choisi n'en télécharge pas le code —, accepter / refuser / personnaliser **au même niveau** (CNIL), reprise permanente par le lien « Cookies » du pied de page, et page `/:lang/privacy` prerendue fr+en.
- Conséquences : `ConsentService` n'injecte que `PLATFORM_ID` et `AnalyticsService` que `ConsentService` — **ni `Router`, ni `AuthService`, ni `HttpClient`** : c'est ce qui permet d'instrumenter les services `core/` sans qu'aucune de leurs ~1000 specs n'ait à fournir un provider de plus (`features/student/` n'injecte aucun service prof, une spec qui l'oublierait échouerait sur `OAuthService`) ; le câblage routeur et identité vit donc dans `app.config.ts`. L'effect de démarrage lit `decision()` **pour lui-même** : un refus ne change pas `analyticsGranted()` (faux avant, faux après) et sans cette dépendance la file d'attente survivrait au refus. Les événements idempotents comptent ce que compte leur cache : `course_viewed` n'est émis que dans la branche du fetch réel, `student_module_opened` sur défaut de cache. Ajouter un événement = une entrée dans `AnalyticsEvents` (le typage impose ses propriétés) + un `capture` là où le signal existe. Le `moduleEvent` du bac à sable reste **non instrumenté** : sans consommateur aujourd'hui, déclaré non fiable (`'unsafe-eval'`), et l'instrumenter toucherait le prompt `MODULE_RUNTIME` du back (TODO.md). Le masquage du replay est un couplage à des **classes de template** (`course-chat__thread`, `exercise-view__revealed-answer`…) qui échouerait en silence : `analytics.masking.spec.ts` le garde. Enfin, `eu.i.posthog.com` est bloqué par les bloqueurs de publicité : sans proxy d'ingestion côté nginx (hors repo), la mesure sous-compte les visiteurs équipés (TODO.md).
- Code : `src/environments/environment.model.ts` (`AnalyticsConfig`) et les 4 fichiers d'environnement ; `core/consent/` (`consent.model.ts`, `consent.service.ts`), `core/analytics/` (`analytics.events.ts`, `scrub.ts`, `analytics.service.ts`), `layout/consent-banner/`, `features/privacy/`, `app.config.ts` (second `provideAppInitializer`), `app.routes.ts` + `app.routes.server.ts` (`:lang/privacy` en `Prerender`), `layout/footer/`, `i18n/{fr,en}/{consent,privacy,footer}.json` ; instrumentation dans `CourseService`, `CourseTransferService`, `ShareLinkService`, `ResourceService`, `ModuleService`, `PublicCourseService`, `StudentSubmissionService`, `SearchService`, `AssistantChatState`, plus `CourseBlocks`, `Onboarding`, `CoursePreview`, `StudentContent`.

## 25. Configurations IA nommées, plusieurs par utilisateur, une active (2026-09-09)

- Contexte : le credential IA personnel était **unique** — sept colonnes `ai_*` sur `users`, une ressource singleton `PUT/DELETE /users/me/ai-credentials`, un signal mono-objet côté front. Changer de provider ou de modèle imposait de ré-écrire la config et de perdre l'ancienne (et sa clé) ; revenir à l'IA par défaut la supprimait. Un prof qui alterne entre une clé cloud et un Ollama local ressaisissait tout à chaque bascule.
- Décision : une table **`ai_configurations`** (une ligne par configuration nommée : `name`, provider, modèle, base_url, clé chiffrée avec un **sel par ligne**, préférences de raisonnement, `is_active`, FK `users` en cascade), **au plus une active par utilisateur** — invariant porté par l'**index partiel unique** `uq_ai_configurations_active (user_id) WHERE is_active` — et **aucune active = IA par défaut** (les configurations sont conservées). Pas de pointeur `users.active_ai_configuration_id` (FK circulaire). **Créer active** la nouvelle configuration (le modèle mental de l'ancien PUT « enregistrer = utiliser » ; revenir à l'IA par défaut reste un clic) ; modifier ne touche pas au statut ; supprimer l'active ramène à l'IA par défaut. Plafond `MAX_CONFIGURATIONS = 10` en service (422, miroir front `AI_CONFIGURATIONS_MAX`). Le chemin `/users/me/ai-credentials` et le nom du paquet sont conservés, la ressource devient une **collection** : GET renvoie l'**enveloppe** (`configurations[]`, `active_id`, état de l'IA par défaut) comme toute route mutante ; `POST` crée et active, `PUT /active {id|null}` bascule (déclaré **avant** `PUT /{id}`), `PUT/DELETE /{id}`, les sondes `/test` et `/models` prennent un `config_id` optionnel (clé omise = clé enregistrée de cette configuration). La cascade `effective_config` lit la configuration **active** (un select de plus), signature inchangée. ## 24. Préférences de raisonnement et d'effort par provider (2026-09-09)

- Contexte : le back relayait déjà le raisonnement des modèles (blocs `reasoning` de langchain-core → événement SSE `thinking`, affiché dans le chat) mais rien ne demandait jamais à un provider de raisonner : `AIRequestConfig` ne portait que provider/modèle/clé/base_url. - Décision : deux préférences **portables** — `reasoning` (null = défaut du modèle, true = demandé et affiché, false = coupé) et `reasoning_effort` (un niveau **natif** du provider, `PROVIDER_REASONING_EFFORTS` : low/medium/high/xhigh/max chez Anthropic, minimal/low/medium/high/xhigh chez OpenAI, minimal/low/medium/high chez Gemini, low/medium/high chez Ollama — chez OpenAI « none » n'est pas un niveau mais l'encodage de « coupé ») — **persistées avec le credential personnel** (`users.ai_reasoning`, `ai_reasoning_effort`), appliquées à tous les chats et au tuteur par la cascade `effective_config` ; pour l'IA par défaut du serveur, c'est l'**opérateur** qui les pose (settings `AI_REASONING` / `AI_REASONING_EFFORT` des `config/<APP_ENV>.yaml`, absents = défaut du modèle, résolus et validés par `resolve_config` avec la même règle de gating `check_reasoning_support`). Les capacités sont déclarées **par provider** dans `app/core/ai/types.py` (`PROVIDERS_WITH_REASONING_TOGGLE`, `PROVIDERS_WITH_REASONING_EFFORT`, miroirs front dans `ai-credentials.model.ts`) : gating **dur** au niveau provider (422 au PUT et à la résolution du fallback, niveaux natifs de `PROVIDER_REASONING_EFFORTS`). Les options réellement **proposées** viennent d'un **catalogue par couple (provider, modèle)** maintenu à la main dans `app/core/ai/reasoning.py` — aucun provider ne publie ses niveaux par API — : règles par préfixe de nom, adossées au profil embarqué de langchain (`app/core/ai/profiles.py`, instance sonde sans réseau : niveaux Anthropic déclarés par modèle, « ne raisonne pas » chez Anthropic/OpenAI/Google) ; servies avec le credential (`reasoning_options`) et par la sonde pure `POST /users/me/ai-credentials/reasoning-options` ; un modèle inconnu reçoit les options génériques du provider (`known=false`, hint au front). Le catalogue **propose, il n'impose pas** : le support par **modèle** reste laissé au provider (ce qui est demandé est transmis, jamais abandonné en silence ; un refus remonte en 422 par `errors.py`). L'encodage vit dans `providers.py`, un helper pur par provider : Anthropic par paliers d'après le profil embarqué du modèle (adaptive + `output_config.effort` ; effort natif + budget ; budget seul), effort toujours via `output_config` ; Gemini par famille de nom ; OpenAI en Chat Completions sans changement de transport ; Ollama `reasoning` booléen ou niveau. `reasoning=false` annule l'effort partout. ## 23. Contexte IA en sommaire, system prompt statique, replay abrégé, cache de prompt (2026-09-08)

- Contexte : le chat consommait ~15 000 tokens d'entrée par message. Les prompts statiques n'y étaient pour rien (700 à 1 700 tokens) : le cours entier était rendu en markdown dans le system prompt (jusqu'à 60 000 caractères, mode sommaire par extraits au-delà) et renvoyé à **chaque appel modèle** d'un tour — un tour compte tous ses appels, et le tuteur en fait au moins deux (`record_verdict`) ; l'historique rejouait en entier résultats d'outils (PDF, modules : 40 000 caractères) et arguments de propositions (markdown, code) ; aucun cache de prompt.
- Décision : (1) le contexte ne porte plus qu'un **sommaire structuré** du cours — blocs, types, description, plan des titres internes parsés du markdown, bibliothèques — **jamais le contenu d'un bloc** ; seule la cible du tour (bloc ou module édité, exercice résolu) est rendue en entier ; le modèle lit le reste à la demande (`read_block`, plusieurs lectures par round). (2) Le system prompt est **statique** par contexte ; le contexte du tour voyage en tête du **message utilisateur**, après l'historique, séparé par `---` — un préfixe stable (system, tools, historique) pour le cache de prompt, même quand la cible change à chaque proposition acceptée. (3) Replay **abrégé et déterministe** : fenêtre à hystérésis (30 → 20 messages ; tuteur 12 → 8 tours), résultats d'outils tronqués à 1 500 caractères, arguments chaîne à 300 (le contenu d'une proposition passée n'est jamais rejoué). (4) Prompts rationalisés : règles impersonnelles partagées assistant/tuteur, protocole HITL énoncé une fois, descriptions de tools sur une ligne, `MODULE_RUNTIME` et catalogue markdown resserrés. (5) **Cache de prompt** : le message `system` de tête devient le `system_prompt` du graphe (hors état, repassé à la reprise HITL) ; middleware Anthropic (`AnthropicPromptCachingMiddleware`, TTL 5 min) pour ce seul provider, OpenAI/Gemini cachant d'eux-mêmes un préfixe stable ; les tokens lus en cache (`cached_input_tokens` ⊂ `input_tokens`) sont remontés dans le SSE, persistés et affichés (« dont N en cache »).
- Conséquences : sur le cours d'exemple, ce qui part par appel modèle passe de 12 955 à 5 103 caractères (contexte `course`), de 16 185 à 8 688 (`block_text`), de 20 140 à 11 640 (`block_exercise`), de 22 427 à 13 208 (`module`, dont 3 300 de code du module édité) et de 14 758 à 8 324 (tuteur) ; sur un cours proche de l'ancien plafond, la baisse dépasse 80 %. Prix assumé : une relecture globale du cours coûte des lectures (`MAX_TOOL_ROUNDS` = 5, plusieurs `read_block` par round encouragés) ; le modèle ne peut plus citer un passage qu'il n'a pas lu. L'écriture de cache Anthropic coûte ×1,25 : rentable dès le 2e appel d'un tour (tuteur) ou le 2e tour dans les 5 minutes. Mistral (provider par défaut des `config/*.yaml`) n'a pas de cache : ses gains viennent des points 1 à 4. Colonne `cached_input_tokens` sur `ai_messages` et `exercise_submissions` (migration). Ce que la persistance garde : les lignes `user` portent la demande brute, jamais le contexte du tour (comme le system prompt).
- Code : `app/course_assistant/prompts.py`, `context.py` (`system_prompt_for`, `render_outline`, `build_turn_context`, `turn_message`), `render.py` (`markdown_outline`, `outline_block`), `replay.py`, `editing/*`, `app/student_exercises/prompts.py`/`context.py`, `app/core/ai/agent.py` (`build_agent(system_prompt=, prompt_cache=)`), `client.py`, `messages.py`, `types.py` (`AIUsage.cached_input_tokens`) ; front `core/course-assistant/usage.ts`, `course-chat.html`, `course-chat-settings.html`.

## 11. Granularité des propositions HITL (avant 2026-09)

## 10. HITL par interrupt/resume LangGraph, checkpointer en mémoire (avant 2026-09)

- Contexte : l'IA doit proposer une modification que le prof accepte ou rejette, sans jamais muter le bloc elle-même.
- Décision : le tool de proposition **fige le run** (`interrupt`), le flux SSE émet `interrupt` et se ferme sans `done` ; la décision rouvre un flux qui **reprend** le run (`Command(resume=…)`) ; **le résultat du tool est la décision** (acceptée/rejetée + commentaire). Checkpointer `InMemorySaver` + registre in-process avec TTL.
- Conséquences : **mono-worker** obligatoire (la reprise doit arriver sur le worker qui tient le checkpoint), reprises perdues au redémarrage, un tour HITL = un appel compté (config réutilisée à la reprise) ; le tool est ré-exécuté depuis le début à la reprise (validation idempotente). Passage à `AsyncPostgresSaver` le jour du multi-nœud (TODO).
- Code : `app/core/ai/client.py` (`agent_interrupt`), `app/course_assistant/editing/base.py` (`hitl_gate`), `app/course_assistant/hitl.py` (`suspend`, seul appelant d'`agent_interrupt` depuis la décision 34 — *révisé le 2026-09-13* : les questions de l'assistant passent par le même interrupt, et tout tour d'assistant est checkpointé).

## 9. Références courtes côté modèle, jamais d'UUID (avant 2026-09)

- Contexte : les modèles déforment les UUID recopiés (~20 tokens aléatoires).
- Décision : l'instantané du tour numérote blocs `B1…`, ressources `R1…`, modules `M1…`, questions `Q1…` ; prompt, tools (avec `enum`) et citations n'utilisent que ces références ; un résolveur tolérant (préfixe d'UUID, titre exact ou approchant) liste les candidats en cas d'échec ; les citations `oc-block:B3` sont **réécrites en UUID en flux**.
- Conséquences : texte streamé = texte persisté ; contrat SSE et front inchangés ; les ids hallucinés sont filtrés des `sources`.
- Code : `app/course_assistant/refs.py`.

## 8. Client IA BYO token, cascade de configuration et quota quotidien (avant 2026-09)

- Contexte : le cadrage initial disait « aucune clé persistée » ; en pratique il faut une clé par prof, et un fallback serveur pour les élèves ou l'essai.
- Décision : cascade **config explicite de la requête > credential utilisateur persistant chiffré** (AES-256-GCM, clé dérivée HKDF d'une clé maître, sel par utilisateur — révisée par la décision 25 : plusieurs configurations nommées par utilisateur, la cascade lit l'**active**, sel par ligne) **> fallback serveur `AI_*`**, ce dernier seul **compté** sous un quota quotidien par utilisateur (`users.ai_daily_call_quota`, NULL = défaut, 0 = illimité, **sans CHECK SQL**, jamais écrit par une route) ; réservation atomique avant l'appel, remboursement si le provider échoue, un flux qui a produit du contenu **reste compté**.
- Conséquences : `app/core/ai/` reste stateless (la cascade vit dans `ai_credentials.service.effective_config`) ; seul `app/core/ai/` importe langchain/langgraph/langfuse, seul `app/core/crypto.py` importe `cryptography` ; une clé refusée par le provider est un **400** (401 réservé au JWT) ; la clé n'apparaît dans aucun schéma de réponse.
- Code : `app/core/ai/`, `app/ai_credentials/`, `app/models/ai_daily_usage.py`.

## 7. Partager un cours expose toute sa bibliothèque (avant 2026-09)

- Décision : le détail public d'un cours embarque toutes ses ressources `available` et les titres de tous ses modules, blocs ou pas ; le front y adosse ses onglets Ressources/Modules.
- Conséquences : assumé et signalé par un avertissement dans l'UI de partage ; le code des modules reste servi module par module. C'est **la raison d'être** de la table séparée `ai_attachments` (décision 42) : une pièce jointe d'un chat de l'assistant n'est pas une `resource`, donc le partage ne l'expose jamais — y verser les fichiers de travail du professeur les aurait rendus visibles de tous ses élèves.
- Code : `app/public/service.py`.

## 6. Liens de partage : capability URL, expiration obligatoire, 404 uniforme (avant 2026-09)

- Décision : token opaque 256 bits stocké **en clair** (recopiable à tout moment), `expires_at` obligatoire (270 jours), révocation soft ; la visibilité `draft` **suspend** les liens sans les supprimer ; toute erreur du régime public est un **404 « Cours introuvable »**, jamais 401/403/410 (aucun oracle) ; le token voyage en `?token=`.
- Conséquences : validité vérifiée à chaque accès en Python ; les routes `/api/v1/public/*` ne portent aucune dépendance JWT ; le front n'y attache jamais de Bearer, même pour un prof connecté.
- Code : `app/share_links/`, `app/public/service.py`, front `app.config.ts` (`customUrlValidation`).

## 5. Un bloc pointeur meurt avec sa cible (avant 2026-09)

- Décision : un bloc `document` pointe une ressource et un bloc `module` un module par une **colonne** FK nullable en `ON DELETE CASCADE` ; supprimer la cible supprime les blocs pointeurs.
- Conséquences : le front recharge le détail du cours après une suppression de ressource/module ; les CHECKs de cohérence limitent `resource_id` aux blocs `document` et `module_id` aux blocs `module`.
- Code : `app/models/block.py`.

## 4. Modules interactifs : code en base, bac à sable sans réseau (avant 2026-09)

- Contexte : le cadrage §5.5 prévoyait un bundle `.zip` sur S3 avec versionnage par clé et des CDN autorisés.
- Décision : un module = **code HTML/CSS/JS stocké en base** et édité dans l'app ; exécution en **iframe sandbox à origine opaque** (`sandbox` statique **sans** `allow-same-origin`) avec une **CSP dans le srcdoc** : `default-src 'none'`, inline et `data:`/`blob:` seuls autorisés, `'unsafe-eval'` toléré (grapheurs), `form-action 'none'` — **aucun réseau sortant**.
- Conséquences : modules self-contained (aucun CDN, aucune police distante — les librairies du catalogue sont inlinées par le runtime, décision 30) ; le prompt `MODULE_RUNTIME` du back est le miroir du contrat de `module-document.ts` — toute évolution de l'un se reporte dans l'autre ; une future CSP d'en-tête posée par l'infra devra tolérer `'unsafe-eval'` ; le srcdoc est posé impérativement (jamais `[srcdoc]`, le sanitizer Angular striperait les scripts).
- Code : `app/modules/`, front `shared/module-runner/module-document.ts`.

## 3. Pas de binaire par le backend — sauf l'export/import de cours (avant 2026-09)

- Contexte : cible Raspberry Pi (RAM, bande passante) ; les uploads sont directs navigateur → S3 par URL présignée.
- Décision : l'API ne transporte jamais de binaire, **à une exception près** : l'archive `.zip` d'export/import est assemblée et parsée par l'API (volumes bornés par `TRANSFER_MAX_ZIP_BYTES`, assemblage dans un fichier temporaire spoolé, jamais une archive entière en RAM).
- Conséquences : seules deux méthodes de bytes dans `storage.py` (`read_object_into`, `put_object`) ; ordre transactionnel de l'import : inserts sans commit → put S3 → commit (au pire un orphelin bucket, jamais une référence DB vers un objet absent) ; la suppression purge S3 **après** commit.
- Code : `app/course_transfer/`, `app/core/storage.py`.

## 2. Une seule extension Postgres, pas de pgvector (avant 2026-09)

- Décision : aucune extension Postgres, à une exception actée pour la recherche : contrib `unaccent` + configuration `french_unaccent` (stemming + insensibilité aux accents). Pas de pgvector ; si la vectorisation se fait, ce sera probablement ChromaDB.
- Conséquences : toute autre extension reste à arbitrer explicitement ; les vecteurs FTS sont maintenus par triggers, jamais par l'ORM, et n'indexent jamais `expected_answer`.
- Code : migration FTS, `app/search/`.

## 1. Resource server pur, IdP remplaçable (avant 2026-09)

- Contexte : le cahier des charges exige de pouvoir changer d'IdP en ne touchant qu'un module par application.
- Décision : la SPA porte tout le flow OIDC (Authorization Code + PKCE vers Zitadel) ; l'API n'émet jamais de token, ne stocke aucune identité et valide le JWT de chaque requête ; la logique IdP est **confinée** dans `app/core/auth.py` (back) et `AuthService` (front, seul importeur d'`angular-oauth2-oidc`).
- Conséquences : `OIDC_AUDIENCE` = client id du front ; Zitadel doit émettre des JWT access tokens ; `get_current_user` ne touche jamais la base (la résolution `sub → users` vit dans `app/users/`) ; token invalide → 401 + `WWW-Authenticate`, IdP injoignable → 503, jamais 500, jamais le token dans les logs.
- Code : `app/core/auth.py`, front `src/app/core/auth/`.
