## 31. Encadrés pédagogiques en syntaxe d'alerte GitHub, dans le pipeline markdown (2026-09-11)

- Contexte : les supports de cours de toutes les matières mettent en valeur définitions, méthodes, points à retenir et mises en garde. Un fence ne convient pas — son contenu est du texte brut, alors qu'un encadré contient formules, listes et figures — et un type de bloc dédié casserait le fil du texte (décision de §5.3 : le markdown couvre les encadrés).
- Décision : la syntaxe des **alertes GitHub**, déjà connue des modèles et des profs qui écrivent du markdown, rendue par le pipeline synchrone : une citation dont la première ligne commence par `[!TYPE]` devient un encadré, le reste de cette ligne est un titre personnalisé (à la manière d'Obsidian), le contenu est du markdown complet. Six types scolaires aux mots-clés français sans accent — `DEFINITION`, `RETENIR`, `METHODE`, `EXEMPLE`, `REMARQUE`, `ATTENTION` — et les cinq mots-clés GitHub en alias (`NOTE`, `TIP`, `IMPORTANT`, `WARNING`, `CAUTION`, plus `EXAMPLE` et `METHOD`) ; casse, accents et espaces indifférents. Ces mots-clés se traduisent en types internes anglais, comme toute clé du code — `definition`, `keypoint`, `method`, `example`, `note`, `warning`, qui nomment les classes CSS et les clés i18n. Titre par défaut dans la **langue de l'interface** (comme « av. J.-C. » des frises), passé au rendu par `markdown-view`. Type inconnu : la citation reste une citation, marqueur visible.
- Conséquences : les mots-clés sont un **contrat de contenu** — stockés dans le markdown des blocs, cités par le catalogue de l'assistant, recopiés par la garde du cours d'exemple côté back — : on en ajoute, on n'en retire ni n'en renomme jamais. Le titre par défaut dépend de la langue : il entre dans la clé du gel de rendu de `markdown-view`. Hors d'OpenCartable (export markdown, GitHub), un encadré reste une alerte ou une citation lisible.
- Code : front `core/markdown/course-callouts.ts`, `course-markdown.ts` (override `blockquote`), `shared/markdown-view/`, `styles/_course-content.scss`, `styles/_print.scss`, `features/docs/callouts-doc/` ; back `app/course_assistant/prompts.py`, `app/starter_course/manifest.json`, `tests/test_starter_course.py`.

## 30. Librairies préinstallées dans le bac à sable des modules, inlinées par le runtime (2026-09-11)

- Contexte : la décision 4 coupe tout réseau aux modules (CSP `default-src 'none'` du srcdoc) : aucun CDN, donc « JavaScript natif écrit à la main ». Les simulations de physique ou de SVT, les graphiques et la 3D restent alors hors de portée de l'assistant comme du prof, et coller une librairie dans le JS stocké est impossible (200 000 caractères par champ, code renvoyé en entier au modèle à chaque tour).
- Décision : six librairies **servies par l'app** et déclarées par un **pragma** en commentaire dans le JS du module, `// @oc-libs: matter, chart` — `matter` (Matter.js 0.20), `chart` (Chart.js 4), `p5` (p5.js **2.x**), `jsxgraph` (JSXGraph 1.x, CSS comprise), `d3` (D3 7), `three` (Three.js, OrbitControls inclus). Le **parent** (origine de l'app) lit leur texte sous `/assets/module-libs/` (préparé au postinstall par `scripts/prepare-module-libs.mjs` : UMD copiés, Three bundlé en IIFE par esbuild, noms de fichiers stables, garde contre `</script`/`<!--`) et l'**inline** dans le srcdoc, entre le bridge et le JS du prof. La **CSP n'est pas rouverte** : `script-src 'unsafe-inline'` couvre ces scripts, l'iframe ne fait aucune requête. Pas de schéma, de colonne ni d'outil IA : le pragma voyage avec le JS (export, import, propositions `propose_js_edit`), un nom inconnu est ignoré (et signalé dans l'éditeur). Pragma plutôt qu'injection systématique : p5 pèse ~1 Mo et son « mode global » s'active dès qu'un module définit `setup`/`draw`.
- Conséquences : composition **asynchrone** quand un pragma est présent (`ModuleLibraryLoader`, cache mémoire par fichier, échec retiré du cache), gardée par un compteur de génération dans `ModuleRunner` ; sans pragma, le chemin synchrone est inchangé. Chaque iframe re-parse sa librairie (pas de cache HTTP du module lui-même — TODO.md). Le catalogue est un **miroir** : `MODULE_LIBRARIES` (front) = `MODULE_LIBRARY_NAMES` et la puce « Bibliothèques » de `MODULE_RUNTIME` (back), qui documente aussi les pièges (dimensionner sur la largeur à cause de l'auto-resize, p5 2.x sans `preload`, aucun chargement par URL). p5 et JSXGraph sont LGPL, servis non modifiés avec leur licence. Le cours d'exemple montre une librairie par module, gardé par des tests (pragmas au catalogue, usage de chaque librairie déclarée, catalogue entièrement couvert).
- Code : front `shared/module-runner/` (`module-libraries.ts`, `module-library-loader.ts`, `module-document.ts`, `module-runner.*`), `features/courses/module-editor/`, `scripts/prepare-module-libs.mjs`, `angular.json` (assets), `src/static-headers.ts` ; back `app/course_assistant/prompts.py`, `app/starter_course/manifest.json`, `tests/test_starter_course.py`.

## 29. Code exécutable côté élève (SQL, Python) : runtimes WASM en Worker, chargés au clic (2026-09-11)

- Contexte : NSI, maths et physique au lycée demandent du code qui tourne — des requêtes SQL, des scripts Python. Un serveur d'exécution est exclu (Raspberry Pi, élèves sans compte, sécurité) : le code doit s'exécuter dans le navigateur de l'élève, en WebAssembly. Mais les runtimes pèsent lourd (sql.js ~0,7 Mo, Pyodide ~13 Mo), un code d'élève peut boucler sans fin, et du code exécuté sur l'origine de l'application ne doit ni lire ses jetons ni contacter un tiers.
- Décision : les fences ```` ```sql ```` et ```` ```python ```` deviennent exécutables (bouton Exécuter, code modifiable par l'élève, sortie sous le code) via une brique commune `RunnableCode`. Le runtime est servi **depuis l'origine** (`/assets/sqljs/`, `/assets/pyodide/`, copiés par `angular.json`, jamais bundlés), téléchargé au **premier clic** — jamais à l'affichage —, tenu par un **service root** et exécuté dans un **Worker** résiliable : délai (5 s par requête SQL), bouton Arrêter, worker tué puis recréé à la demande. Le serveur SSR pose une **CSP d'en-tête sur les scripts de worker** (`default-src 'none'; script-src 'self' 'wasm-unsafe-eval'; connect-src 'self'` — la CSP d'un worker vient de son script, pas du document) et `Cache-Control: no-cache` sur les runtimes non hashés. SQL : sql.js dans son propre worker classique, base neuve à chaque exécution (préparation avant `-- @query`, puis la requête). Python : Pyodide 314 dans un worker **module** bundlé par Angular (Pyodide chargé à l'exécution depuis `/assets/pyodide/`), avec numpy et matplotlib : leurs 12 wheels sont téléchargées au postinstall depuis la distribution officielle de la même version et **vérifiées par sha256**, et le lock servi est **élagué** aux paquets hébergés (tout autre import lève `ModuleNotFoundError`) ; `MPLBACKEND=Agg`, figures sérialisées en PNG en fin d'exécution, délai de 15 s armé une fois Python et les paquets chargés.
- Conséquences : un Worker n'a ni DOM ni stockage (aucun accès aux jetons OIDC) et, en production, ne peut joindre que l'origine ; `ng serve` ne pose pas ces en-têtes (vérification sous `serve:ssr`). Si nginx ajoute sa propre CSP, elle se cumule à celle du worker et doit autoriser `'wasm-unsafe-eval'` (TODO.md). Les blocs sont indépendants (aucun état partagé entre deux exécutions) ; les exécutions d'une page sont sérialisées sur un seul worker. Les fences ```` ```sql ```` existants et ceux écrits par l'assistant, chat compris, deviennent exécutables — voulu. Le manifeste du cours d'exemple est gardé par une **vraie exécution** dans `sqlite3` et par la compilation des programmes Python (imports limités aux paquets hébergés) pendant pytest. Vérifié en navigateur sous la CSP de production : Pyodide, numpy et matplotlib se chargent, et un `fetch` Python vers une autre origine échoue (il passe sous `ng serve`, sans l'en-tête). `npm install` a besoin du réseau pour les wheels (`OC_SKIP_PYODIDE_PACKAGES=1` pour s'en passer) ; Pyodide exige Chrome 112, Firefox 114 ou Safari 16.4.
- Code : front `shared/markdown-extensions/runnable-code/`, `shared/markdown-extensions/sql/` (`sql-runtime.ts`, `sql-config.ts`, `sql-view.ts`), `shared/markdown-extensions/python/` (`python.worker.ts`, `python-runtime.ts`, `python-output.ts`, `python-view.ts`), `scripts/prepare-pyodide.mjs`, `src/static-headers.ts`, `src/server.ts`, `angular.json` (assets), `.dockerignore` ; back `app/course_assistant/prompts.py`, `tests/test_starter_course.py`.

## 28. Graphiques Vega-Lite rendus en SVG statique durci (2026-09-11)

- Contexte : les graphiques de données (mesures de TP, climatogrammes, données démographiques) manquaient au markdown de cours. Vega-Lite est une grammaire JSON que les modèles connaissent bien et qui produit du SVG (donc imprimable), mais Vega compile par défaut ses expressions en `new Function`, sait charger des données (`data.url`), des images et suivre des liens : un contenu de cours pourrait faire partir des requêtes du navigateur de chaque élève vers un tiers, et exigerait `'unsafe-eval'` sous une CSP stricte.
- Décision : fence ```` ```vegalite ```` rendu **statique et hermétique**. La spec est refusée si elle porte une clé `url` à n'importe quel niveau (données en ligne `data.values` seulement, message explicite) ; les expressions passent par `vega-interpreter` (`parse(…, {ast: true})`), jamais par `new Function` ; le loader rejette tout `load` et tout `sanitize` (aucune requête, aucun `href`) ; la vue tourne sans renderer et `toSVG()` produit un SVG texte re-sanitisé par DOMPurify, posé sur la planche claire fixe `--figure-board`. Pas de `vega-embed` (menu d'actions et thèmes inutiles).
- Conséquences : aucune interactivité (info-bulles, sélections — TODO.md) ; couleurs du thème Vega figées, d'où la planche claire ; ~250 ko gzip de chunks paresseux payés seulement par une page qui affiche un graphique ; les `id` des clips et dégradés du SVG sont rendus uniques à l'impression (`uniquifySvgIds`). Le catalogue de l'assistant (`MARKDOWN_SYNTAXES`) rappelle « jamais d'url » et le manifeste du cours d'exemple est gardé par un test.
- Code : front `shared/markdown-extensions/vegalite/` (`vegalite-config.ts` garde et largeur, `vegalite-view.ts` rendu), `shared/markdown-editor/course-monaco-lang.ts` (fence coloré en JSON), `shared/print/print-transform.ts` ; back `app/course_assistant/prompts.py`, `tests/test_starter_course.py`.

## 27. Mode « Édition auto » des propositions HITL, purement front (2026-09-10)

- Contexte : chaque proposition d'édition de l'assistant (bloc texte, exercice, module) fige le run (`interrupt`, décision 10) et attend un clic Accepter / Rejeter dans la revue qui remplace l'éditeur. Sur une série d'éditions demandées d'affilée, ce clic systématique devient une friction ; il fallait un mode où l'assistant édite sans demander, facile à basculer.
- Décision : deux modes, **Demander** (défaut) et **Édition auto**, portés par un interrupteur du pied des **seuls chats d'édition** (`CourseChatSettings`, input `editing` — ni le panneau global, en lecture seule, ni le tuteur élève). **Aucun changement back** : la route de décision ne mute jamais la cible — c'est déjà le front qui applique la proposition, flush l'autosave puis POST `{accepted: true}` ; le mode auto fait ce clic à la place du professeur, par le même chemin (`ProposalHost`). Préférence **du navigateur** (`localStorage` `oc-assistant-proposal-mode`, commune à tous les éditeurs, défaut `ask`), pas du compte : pas de colonne ni de route pour un confort d'interface. `exercise_question_delete` reste **toujours revue** (`ALWAYS_REVIEWED_KINDS`) : non annulable par Ctrl-Z et référencée par des tentatives d'élèves. Le mode est lu **une fois, à l'arrivée** de la proposition : le basculer pendant une revue ne la décide pas.
- Conséquences : `ProposalHost` porte un effect (dep `autoAccept`, donc un contexte d'injection à la construction) qui applique puis reprend dès que `pendingProposal` change — effect de vue, il tourne avant le rendu de l'hôte : `review` reste `null` et la revue n'apparaît jamais. Il fige l'« original » de la revue AVANT l'application (computed paresseux), une tentative par id : cible disparue (`target`) ou reprise en échec (`decision`) retombent sur la revue manuelle avec le vrai diff. L'éditeur n'est plus masqué sur `pending()` mais sur `review()`. Le modèle n'est pas prévenu du mode (le résultat du tool dit « accepté » comme après un clic) ; une série d'acceptations reste bornée par `MAX_TOOL_ROUNDS` par tour, et Ctrl-Z annule une application texte ou module. Mesure : `assistant_proposal_decided` gagne `auto`, `assistant_proposal_mode_changed` compte les bascules.
- Code : front `core/course-assistant/proposal-mode.service.ts`, `proposal-host.ts`, `proposals.ts` (`ProposalMode`, `ALWAYS_REVIEWED_KINDS`), `assistant-chat-state.ts`, `core/analytics/analytics.events.ts`, `features/course-assistant/course-chat/course-chat-settings.*`, `features/course-assistant/proposal-review/block-proposal-host.ts`, `features/courses/block-editor/`, `features/courses/module-editor/`, `i18n/{fr,en}/courseChat.json`.

## 26. Mesure d'audience PostHog en opt-in strict, URLs nettoyées avant envoi (2026-09-10)

- Contexte : le projet n'avait **aucune mesure d'audience** et **aucun cookie** (décision 21), donc aucune idée de ce que ses utilisateurs font — combien de profs créent un cours, combien de liens partagés sont réellement ouverts, si le tuteur sert. Deux contraintes propres à OpenCartable interdisaient de brancher un SDK tel quel : le public inclut des **élèves mineurs sur des pages publiques anonymes**, et le **token de partage est un segment d'URL** (`/:lang/shared/<token>/…`, décision 6) — une capability URL, que `$current_url` aurait expédiée à PostHog à chaque événement, donnant à quiconque lit le dashboard l'accès en clair aux cours partagés. Même problème avec `?q=` de `/search`, et avec le titre du document, que `SeoService` renseigne avec le titre du cours consulté.
- Décision : mesure **par environnement** (`environment.analytics` : `enabled`, `posthogKey`, `posthogHost`, `sessionReplay` — garde dure `enabled && posthogKey non vide`, sinon **inerte**) et **opt-in strict** : posthog-js n'est même pas **téléchargé** avant consentement (`await import('posthog-js')`, jamais d'import statique — le bundle initial est budgété à 1 Mo et un déploiement qui ne mesure rien ne doit rien payer). Le consentement vit dans un service **indépendant de PostHog** (`core/consent/`, clé `oc-consent`, version + péremption à 6 mois, refus persisté aussi longtemps qu'un accord), lu **après hydratation** (`afterNextRender`) parce que la home et la page de confidentialité sont prerendues. Tout ce qui sort passe par `scrubEvent` posé en `before_send` : query et fragment supprimés, segment après `shared` réécrit `:token`, UUID réécrits `:id`, titre du document retiré — PostHog ne voit que des **motifs de route**. Sous consentement, la **mesure est large et assumée** : `autocapture`, clics de rage, clics morts, cartes de chaleur, performances de chargement, exceptions JS, vues de page par `history_change`, plus les événements explicites de la carte typée `analytics.events.ts` ; seuls les sondages sont coupés. `person_profiles: 'always'` (un profil de visiteur pour tous, élèves anonymes compris) et `persistence: 'localStorage+cookie'` — la décision 21 porte sur l'**API** (Bearer, `allow_credentials: false`) et n'interdit rien au front ; le cookie reste sur l'hôte exact (`cross_subdomain_cookie: false`, l'API vit sur un sous-domaine frère) et `secure_cookie` suit `production`. **`//flags` n'est jamais coupé** : replay, cartes de chaleur et autocapture y lisent leur configuration distante — `advanced_disable_flags: true` rendrait `startSessionRecording()` silencieux. Replay désactivé par défaut, **jamais sur une page élève** (il filmerait des réponses de mineurs), `maskAllInputs` partout et `maskTextSelector` sur les sorties du modèle et les corrigés (`REPLAY_MASK_SELECTOR`). Un prof connecté est identifié par son **`sub` OIDC seul**, jamais son email ni son nom. Règle d'or des propriétés **des événements explicites** : un **énuméré ou un compteur**, jamais de contenu, de saisie ni d'identifiant (l'autocapture, elle, enregistre le libellé de l'élément cliqué — assumé et écrit dans la page de confidentialité). Bannière non modale montée dans le shell (donc sur les pages élèves aussi) mais **derrière un `@defer`** — un visiteur qui a déjà choisi n'en télécharge pas le code —, accepter / refuser / personnaliser **au même niveau** (CNIL), reprise permanente par le lien « Cookies » du pied de page, et page `/:lang/privacy` prerendue fr+en.
- Conséquences : `ConsentService` n'injecte que `PLATFORM_ID` et `AnalyticsService` que `ConsentService` — **ni `Router`, ni `AuthService`, ni `HttpClient`** : c'est ce qui permet d'instrumenter les services `core/` sans qu'aucune de leurs ~1000 specs n'ait à fournir un provider de plus (`features/student/` n'injecte aucun service prof, une spec qui l'oublierait échouerait sur `OAuthService`) ; le câblage routeur et identité vit donc dans `app.config.ts`. L'effect de démarrage lit `decision()` **pour lui-même** : un refus ne change pas `analyticsGranted()` (faux avant, faux après) et sans cette dépendance la file d'attente survivrait au refus. Les événements idempotents comptent ce que compte leur cache : `course_viewed` n'est émis que dans la branche du fetch réel, `student_module_opened` sur défaut de cache. Ajouter un événement = une entrée dans `AnalyticsEvents` (le typage impose ses propriétés) + un `capture` là où le signal existe. Le `moduleEvent` du bac à sable reste **non instrumenté** : sans consommateur aujourd'hui, déclaré non fiable (`'unsafe-eval'`), et l'instrumenter toucherait le prompt `MODULE_RUNTIME` du back (TODO.md). Le masquage du replay est un couplage à des **classes de template** (`course-chat__thread`, `exercise-view__revealed-answer`…) qui échouerait en silence : `analytics.masking.spec.ts` le garde. Enfin, `eu.i.posthog.com` est bloqué par les bloqueurs de publicité : sans proxy d'ingestion côté nginx (hors repo), la mesure sous-compte les visiteurs équipés (TODO.md).
- Code : `src/environments/environment.model.ts` (`AnalyticsConfig`) et les 4 fichiers d'environnement ; `core/consent/` (`consent.model.ts`, `consent.service.ts`), `core/analytics/` (`analytics.events.ts`, `scrub.ts`, `analytics.service.ts`), `layout/consent-banner/`, `features/privacy/`, `app.config.ts` (second `provideAppInitializer`), `app.routes.ts` + `app.routes.server.ts` (`:lang/privacy` en `Prerender`), `layout/footer/`, `i18n/{fr,en}/{consent,privacy,footer}.json` ; instrumentation dans `CourseService`, `CourseTransferService`, `ShareLinkService`, `ResourceService`, `ModuleService`, `PublicCourseService`, `StudentSubmissionService`, `SearchService`, `AssistantChatState`, plus `CourseBlocks`, `Onboarding`, `CoursePreview`, `StudentContent`.

## 25. Configurations IA nommées, plusieurs par utilisateur, une active (2026-09-09)

- Contexte : le credential IA personnel était **unique** — sept colonnes `ai_*` sur `users`, une ressource singleton `PUT/DELETE /users/me/ai-credentials`, un signal mono-objet côté front. Changer de provider ou de modèle imposait de ré-écrire la config et de perdre l'ancienne (et sa clé) ; revenir à l'IA par défaut la supprimait. Un prof qui alterne entre une clé cloud et un Ollama local ressaisissait tout à chaque bascule.
- Décision : une table **`ai_configurations`** (une ligne par configuration nommée : `name`, provider, modèle, base_url, clé chiffrée avec un **sel par ligne**, préférences de raisonnement, `is_active`, FK `users` en cascade), **au plus une active par utilisateur** — invariant porté par l'**index partiel unique** `uq_ai_configurations_active (user_id) WHERE is_active` — et **aucune active = IA par défaut** (les configurations sont conservées). Pas de pointeur `users.active_ai_configuration_id` (FK circulaire). **Créer active** la nouvelle configuration (le modèle mental de l'ancien PUT « enregistrer = utiliser » ; revenir à l'IA par défaut reste un clic) ; modifier ne touche pas au statut ; supprimer l'active ramène à l'IA par défaut. Plafond `MAX_CONFIGURATIONS = 10` en service (422, miroir front `AI_CONFIGURATIONS_MAX`). Le chemin `/users/me/ai-credentials` et le nom du paquet sont conservés, la ressource devient une **collection** : GET renvoie l'**enveloppe** (`configurations[]`, `active_id`, état de l'IA par défaut) comme toute route mutante ; `POST` crée et active, `PUT /active {id|null}` bascule (déclaré **avant** `PUT /{id}`), `PUT/DELETE /{id}`, les sondes `/test` et `/models` prennent un `config_id` optionnel (clé omise = clé enregistrée de cette configuration). La cascade `effective_config` lit la configuration **active** (un select de plus), signature inchangée. Migration à la main : copie du credential existant en première configuration active nommée « provider · modèle », puis suppression des colonnes `users.ai_*` et de leurs CHECKs. Front : signal en enveloppe, écran Réglages IA en liste de radios-cartes (IA par défaut + une par configuration, cocher = `PUT /active` immédiat, actions Modifier/Supprimer hors du label) avec un éditeur de création/modification (champ **nom après le password**, parade Firefox intacte), et **menu rapide** dans l'engrenage du pied du chat (`menuitemradio` par choix, puis « Gérer les configurations… » vers la modale) ; le libellé « nom · modèle » du pied est un **sélecteur de modèle** (panneau à champ d'autocomplétion sur les modèles du provider, listés avec la clé enregistrée de l'active via `config_id`, saisie libre sinon) qui enregistre le modèle sur la configuration active en ramenant ses préférences de raisonnement dans les options du nouveau modèle.
- Conséquences : désactivation et activation sont **deux instructions** (UPDATE Core puis mutation ORM) — l'index partiel unique n'est pas différable ; toute fixture FIFO qui traverse la cascade gagne un slot `[config active]` ou `[]` après le `[user]` de `get_or_create_by_sub` ; le pied du chat écrit ses préférences de raisonnement sur la configuration **active** (`update(active.id, …)`) et l'éditeur ne se réaligne que sur la configuration qu'il édite ; le quota quotidien reste **par utilisateur** (`users.ai_daily_call_quota`, `ai_daily_usage`) ; `ai_messages.provider` continue de porter le provider du tour (rien ne référence une configuration par id) ; downgrade best-effort (seule l'active revient sur `users.ai_*`).
- Code : `app/models/ai_configuration.py`, `app/models/user.py`, `alembic/versions/7d2e91c4a6b8_configurations_ia_nommees.py`, `app/ai_credentials/schemas.py` (`AICredentialsRead` enveloppe, `AIConfigurationIn`, `ActiveConfigurationIn`), `service.py` (`create_configuration`, `update_configuration`, `delete_configuration`, `set_active_configuration`, `effective_config`), `router.py` ; front `core/ai-credentials/ai-credentials.model.ts` (`AiConfiguration`, `activeConfiguration`), `ai-credentials.service.ts` (`create`/`update`/`remove`/`activate`), `ai-credentials-form.ts` (`payloadFromConfiguration`, `testPayloadFromForm`), `features/settings/ai-settings/`, `features/course-assistant/course-chat/course-chat-settings.*`.

## 24. Préférences de raisonnement et d'effort par provider (2026-09-09)

- Contexte : le back relayait déjà le raisonnement des modèles (blocs `reasoning` de langchain-core → événement SSE `thinking`, affiché dans le chat) mais rien ne demandait jamais à un provider de raisonner : `AIRequestConfig` ne portait que provider/modèle/clé/base_url. Les API divergent — Anthropic (`thinking` adaptatif ou à budget, `output_config.effort`), OpenAI (`reasoning_effort`), Gemini (`thinking_level` sur 3+, `thinking_budget` sur 2.x, `include_thoughts`), Ollama (`think`), rien chez Mistral et HuggingFace — et le support dépend aussi du modèle.
- Décision : deux préférences **portables** — `reasoning` (null = défaut du modèle, true = demandé et affiché, false = coupé) et `reasoning_effort` (un niveau **natif** du provider, `PROVIDER_REASONING_EFFORTS` : low/medium/high/xhigh/max chez Anthropic, minimal/low/medium/high/xhigh chez OpenAI, minimal/low/medium/high chez Gemini, low/medium/high chez Ollama — chez OpenAI « none » n'est pas un niveau mais l'encodage de « coupé ») — **persistées avec le credential personnel** (`users.ai_reasoning`, `ai_reasoning_effort`), appliquées à tous les chats et au tuteur par la cascade `effective_config` ; pour l'IA par défaut du serveur, c'est l'**opérateur** qui les pose (settings `AI_REASONING` / `AI_REASONING_EFFORT` des `config/<APP_ENV>.yaml`, absents = défaut du modèle, résolus et validés par `resolve_config` avec la même règle de gating `check_reasoning_support`). Les capacités sont déclarées **par provider** dans `app/core/ai/types.py` (`PROVIDERS_WITH_REASONING_TOGGLE`, `PROVIDERS_WITH_REASONING_EFFORT`, miroirs front dans `ai-credentials.model.ts`) : gating **dur** au niveau provider (422 au PUT et à la résolution du fallback, niveaux natifs de `PROVIDER_REASONING_EFFORTS`). Les options réellement **proposées** viennent d'un **catalogue par couple (provider, modèle)** maintenu à la main dans `app/core/ai/reasoning.py` — aucun provider ne publie ses niveaux par API — : règles par préfixe de nom, adossées au profil embarqué de langchain (`app/core/ai/profiles.py`, instance sonde sans réseau : niveaux Anthropic déclarés par modèle, « ne raisonne pas » chez Anthropic/OpenAI/Google) ; servies avec le credential (`reasoning_options`) et par la sonde pure `POST /users/me/ai-credentials/reasoning-options` ; un modèle inconnu reçoit les options génériques du provider (`known=false`, hint au front). Le catalogue **propose, il n'impose pas** : le support par **modèle** reste laissé au provider (ce qui est demandé est transmis, jamais abandonné en silence ; un refus remonte en 422 par `errors.py`). L'encodage vit dans `providers.py`, un helper pur par provider : Anthropic par paliers d'après le profil embarqué du modèle (adaptive + `output_config.effort` ; effort natif + budget ; budget seul), effort toujours via `output_config` ; Gemini par famille de nom ; OpenAI en Chat Completions sans changement de transport ; Ollama `reasoning` booléen ou niveau. `reasoning=false` annule l'effort partout. UI : deux `<select>` natifs après le modèle dans Réglages IA et deux sélecteurs compacts dans le pied du chat qui enregistrent aussitôt par le PUT du credential reconstruit (clé omise = conservée).
- Conséquences : ajouter un provider capable = deux frozensets (back et front) + un helper d'encodage ; un modèle inconnu du profil Anthropic est traité comme récent (adaptive) — la lib ne valide la forme de `thinking` qu'à la requête, un mauvais palier serait un 503 en plein flux ; « coupé » n'est pas proposé pour Gemini 3 ni 2.5 Pro (non désactivables ; posé par l'API, il vaut `low`/`thinking_budget 0`) ni pour les modèles OpenAI sans « none » (o-series, gpt-5) ; le catalogue est une dette d'entretien à chaque nouvelle famille de modèles (TODO.md) ; les **règles par préfixe doivent se suffire** — le profil embarqué est une donnée tierce dont le contenu change d'une version du paquet partenaire à l'autre (`langchain-google-genai` 4.4 a retiré l'entrée `gemini-2.0-flash`, d'où des options proposées à un modèle qui n'en a pas sur l'image de préprod), donc une famille qui ne raisonne pas a sa règle en dur et la table de test du catalogue s'exécute **profil neutralisé**, la branche profil étant testée à profils explicites ; le pin exact de `requirements.txt` borne le risque à une montée de version délibérée sans l'annuler ; deux écrivains du même credential (formulaire et pied du chat) sont réconciliés par le signal d'`AiCredentialsService` — un formulaire non modifié se réaligne ; un changement au pied entre un `interrupt` et la décision ne s'applique pas à la reprise (`pending.config` réutilisé) ; un `AI_REASONING*` invalide ou hors capacités rend le fallback inutilisable (422 à la résolution, jamais un crash au boot) et n'est pas affiché au front (TODO.md).
- Code : `app/core/ai/types.py` (`PROVIDER_REASONING_EFFORTS`, `check_reasoning_support`), `reasoning.py` (catalogue), `profiles.py`, `providers.py`, `client.py` (`resolve_config`), `app/core/config.py`, `app/ai_credentials/schemas.py` (`ReasoningOptionsRead`), `service.py`, `router.py`, `app/models/user.py` ; front `core/ai-credentials/ai-credentials.model.ts`, `ai-credentials-form.ts` (`reasoningToggleVisible`, `reasoningEffortVisible`, `alignReasoningWithOptions`, `payloadFromCredentials`), `features/settings/ai-settings/`, `features/course-assistant/course-chat/course-chat-settings.*`.

## 23. Contexte IA en sommaire, system prompt statique, replay abrégé, cache de prompt (2026-09-08)

- Contexte : le chat consommait ~15 000 tokens d'entrée par message. Les prompts statiques n'y étaient pour rien (700 à 1 700 tokens) : le cours entier était rendu en markdown dans le system prompt (jusqu'à 60 000 caractères, mode sommaire par extraits au-delà) et renvoyé à **chaque appel modèle** d'un tour — un tour compte tous ses appels, et le tuteur en fait au moins deux (`record_verdict`) ; l'historique rejouait en entier résultats d'outils (PDF, modules : 40 000 caractères) et arguments de propositions (markdown, code) ; aucun cache de prompt.
- Décision : (1) le contexte ne porte plus qu'un **sommaire structuré** du cours — blocs, types, description, plan des titres internes parsés du markdown, bibliothèques — **jamais le contenu d'un bloc** ; seule la cible du tour (bloc ou module édité, exercice résolu) est rendue en entier ; le modèle lit le reste à la demande (`read_block`, plusieurs lectures par round). (2) Le system prompt est **statique** par contexte ; le contexte du tour voyage en tête du **message utilisateur**, après l'historique, séparé par `---` — un préfixe stable (system, tools, historique) pour le cache de prompt, même quand la cible change à chaque proposition acceptée. (3) Replay **abrégé et déterministe** : fenêtre à hystérésis (30 → 20 messages ; tuteur 12 → 8 tours), résultats d'outils tronqués à 1 500 caractères, arguments chaîne à 300 (le contenu d'une proposition passée n'est jamais rejoué). (4) Prompts rationalisés : règles impersonnelles partagées assistant/tuteur, protocole HITL énoncé une fois, descriptions de tools sur une ligne, `MODULE_RUNTIME` et catalogue markdown resserrés. (5) **Cache de prompt** : le message `system` de tête devient le `system_prompt` du graphe (hors état, repassé à la reprise HITL) ; middleware Anthropic (`AnthropicPromptCachingMiddleware`, TTL 5 min) pour ce seul provider, OpenAI/Gemini cachant d'eux-mêmes un préfixe stable ; les tokens lus en cache (`cached_input_tokens` ⊂ `input_tokens`) sont remontés dans le SSE, persistés et affichés (« dont N en cache »).
- Conséquences : sur le cours d'exemple, ce qui part par appel modèle passe de 12 955 à 5 103 caractères (contexte `course`), de 16 185 à 8 688 (`block_text`), de 20 140 à 11 640 (`block_exercise`), de 22 427 à 13 208 (`module`, dont 3 300 de code du module édité) et de 14 758 à 8 324 (tuteur) ; sur un cours proche de l'ancien plafond, la baisse dépasse 80 %. Prix assumé : une relecture globale du cours coûte des lectures (`MAX_TOOL_ROUNDS` = 5, plusieurs `read_block` par round encouragés) ; le modèle ne peut plus citer un passage qu'il n'a pas lu. L'écriture de cache Anthropic coûte ×1,25 : rentable dès le 2e appel d'un tour (tuteur) ou le 2e tour dans les 5 minutes. Mistral (provider par défaut des `config/*.yaml`) n'a pas de cache : ses gains viennent des points 1 à 4. Colonne `cached_input_tokens` sur `ai_messages` et `exercise_submissions` (migration). Ce que la persistance garde : les lignes `user` portent la demande brute, jamais le contexte du tour (comme le system prompt).
- Code : `app/course_assistant/prompts.py`, `context.py` (`system_prompt_for`, `render_outline`, `build_turn_context`, `turn_message`), `render.py` (`markdown_outline`, `outline_block`), `replay.py`, `editing/*`, `app/student_exercises/prompts.py`/`context.py`, `app/core/ai/agent.py` (`build_agent(system_prompt=, prompt_cache=)`), `client.py`, `messages.py`, `types.py` (`AIUsage.cached_input_tokens`) ; front `core/course-assistant/usage.ts`, `course-chat.html`, `course-chat-settings.html`.

## 22. Cours d'exemple seedé à l'onboarding, manifeste JSON sans binaire (2026-09-06)

- Contexte : un prof qui termine son onboarding arrive sur un « Mes cours » vide et n'a aucun moyen de découvrir les possibilités d'écriture (formules, diagrammes, figures, schémas, exercices, modules) sans aller lire les pages de doc. Aucun contenu de démo n'existait dans le projet.
- Décision : la **première** complétion d'un profil de prof dépose automatiquement un cours « Cours d'exemple » en `draft` — visite guidée de ces syntaxes, `preview_settings` personnalisés —, en **best effort** après le commit du profil ; le rattrapage manuel est `POST /courses/starter`, exposé par un bouton de l'état vide de « Mes cours ». Le contenu est un `manifest.json` du format d'échange v2 embarqué dans `app/starter_course/`, **sans aucune ressource binaire** (blocs `text`/`exercise`/`module` seulement).
- Conséquences : la phase base de données de l'import est extraite en `insert_manifest_course` (`app/course_transfer/importer.py`) et partagée — son ordre des execute reste le contrat unique, rejoué par deux suites de tests ; le seed n'a **aucune** dépendance `Storage` et n'appelle jamais S3 (garde `load_manifest` : un manifeste porteur de ressources est refusé, sinon des lignes `available` pointeraient des objets absents) ; une erreur de seed est journalisée et rollbackée, jamais propagée — l'onboarding reste un 200, et le `logger.warning` est le seul témoin en production ; la FIFO d'`update_profile` s'allonge de trois résultats à la première complétion d'un prof, et son `IndexError` étant avalé par le best-effort, un test dédié garantit que le seed s'exécute vraiment ; le manifeste se régénère par `GET /courses/{id}/export` sur un cours composé dans l'UI plutôt qu'à la main (le LaTeX échappé en JSON est la principale source d'erreur) ; `POST /courses/starter` ne déduplique pas, miroir de l'import.
- Code : `app/starter_course/` (`manifest.json`, `service.py`, `router.py`), `app/course_transfer/importer.py` (`insert_manifest_course`), `app/users/service.py` (`update_profile`) ; front `CourseService.loadStarterCourse`, `features/courses/course-list/`.

## 21. Preprod : front et API sur deux origines distinctes (2026-09-06)

- Contexte : la preprod est publiée sur deux vhosts — SPA sur `preprod.opencartable.com`, API sur `api.preprod.opencartable.com` — alors que le contrat par défaut (`apiUrl: '/api'`) supposait une origine unique servie par un seul nginx.

Le SSR n'appelle aucune route API (toutes les pages qui consomment l'API sont `RenderMode.Client`), donc l'URL absolue n'a pas de contrepartie serveur.
- Code : `OpenCartableFront/src/environments/environment.preprod.ts`, `OpenCartableBack/config/preprod.yaml`, `app/main.py` (montage conditionnel du `CORSMiddleware`).

## 16. Monaco : AMD depuis les assets, jamais sous `@if`, propositions appliquées en édits annulables (avant 2026-09)

- Contexte : Monaco (~16 Mo) ne doit pas entrer dans le bundle ; recréer l'éditeur à chaque bascule d'onglet perdrait l'état ; une proposition de l'IA appliquée par `setValue` viderait la pile d'annulation.
- Décision : Monaco est servi en AMD depuis `/monaco/vs` avec un `baseUrl` absolu ; ses hôtes le masquent par `[hidden]` ou une classe, **jamais** par `@if` ; une proposition acceptée est appliquée par `executeEdits` **entre deux undo stops** (Ctrl-Z l'annule comme une frappe), avec repli `setValue` si Monaco n'est pas prêt.

## 14. Purge des données : un job hors API, qui vérifie le schéma au lieu d'ordonner les conteneurs (avant 2026-09)

- Contexte : la réconciliation des orphelins S3 énumère tout le bucket (contrainte Pi : déporter le lourd) ; `depends_on: service_healthy` n'ordonne que la première mise en route (reboot du Pi, déploiement avec nouvelle migration alors que le job tourne déjà).
- Décision : la purge est un **service compose `purge`** (même image, boucle shell qui lance `python -m app.maintenance` puis dort ; entrypoint écrasé pour ne pas rejouer les migrations) ; avant d'écrire, le job compare la révision alembic en base à la tête de l'image et **renonce** si elles diffèrent. Défauts prudents : conversations IA et tentatives d'élèves **désactivées** (0), réconciliation S3 en `dry_run`, plancher de 2 jours sur `ai_daily_usage` (quota vivant + remboursement de la veille). Tous les délais vivent dans `config/*.yaml`.
- Conséquences : ne pas remettre la purge dans le process uvicorn ; le service doit figurer dans le compose de preprod (sinon `--remove-orphans` le détruit) ; l'allègement des tours `tool` est un `UPDATE` (la ligne doit survivre pour rester appariée).
- Code : `app/maintenance/` (`schema.py` = garde de schéma).

## 12. Tuteur d'exercice : élève authentifié, imputé à sa config, persistant, révélation bornée serveur (avant 2026-09)

## 11. Granularité des propositions HITL (avant 2026-09)

- Décision : bloc texte = **remplacement entier** du markdown ; exercice = **une opération par question** (sujet, énoncé/corrigé, ajout, suppression — jamais un remplacement de l'exercice) ; module = **un fichier à la fois** (HTML, CSS ou JS, contenu intégral). Une proposition à la fois, le modèle enchaîne après chaque décision. Pendant la revue d'un module, l'aperçu sandbox **exécute déjà le code proposé**.
- Conséquences : Ctrl-Z complet pour le texte et les trois fichiers d'un module ; partiel pour l'exercice (corrigé/ajout/suppression passent par le formulaire) ; les questions sont désignées par des références `Q…` stables le temps d'un tour.
- Code : `app/course_assistant/editing/{block_text,block_exercise,module}.py`, front `core/course-assistant/proposals.ts`.

## 10. HITL par interrupt/resume LangGraph, checkpointer en mémoire (avant 2026-09)

- Contexte : l'IA doit proposer une modification que le prof accepte ou rejette, sans jamais muter le bloc elle-même.
- Décision : le tool de proposition **fige le run** (`interrupt`), le flux SSE émet `interrupt` et se ferme sans `done` ; la décision rouvre un flux qui **reprend** le run (`Command(resume=…)`) ; **le résultat du tool est la décision** (acceptée/rejetée + commentaire). Checkpointer `InMemorySaver` + registre in-process avec TTL.
- Conséquences : **mono-worker** obligatoire (la reprise doit arriver sur le worker qui tient le checkpoint), reprises perdues au redémarrage, un tour HITL = un appel compté (config réutilisée à la reprise) ; le tool est ré-exécuté depuis le début à la reprise (validation idempotente). Passage à `AsyncPostgresSaver` le jour du multi-nœud (TODO).
- Code : `app/core/ai/client.py` (`agent_interrupt`), `app/course_assistant/editing/base.py` (`hitl_gate`, seul appelant), `app/course_assistant/hitl.py`.

## 9. Références courtes côté modèle, jamais d'UUID (avant 2026-09)

- Contexte : les modèles déforment les UUID recopiés (~20 tokens aléatoires).
- Décision : l'instantané du tour numérote blocs `B1…`, ressources `R1…`, modules `M1…`, questions `Q1…` ; prompt, tools (avec `enum`) et citations n'utilisent que ces références ; un résolveur tolérant (préfixe d'UUID, titre exact ou approchant) liste les candidats en cas d'échec ; les citations `oc-block:B3` sont **réécrites en UUID en flux**.
- Conséquences : texte streamé = texte persisté ; contrat SSE et front inchangés ; les ids hallucinés sont filtrés des `sources`.
- Code : `app/course_assistant/refs.py`.

## 8. Client IA BYO token, cascade de configuration et quota quotidien (avant 2026-09)

- Contexte : le cadrage initial disait « aucune clé persistée » ; en pratique il faut une clé par prof, et un fallback serveur pour les élèves ou l'essai.
- Décision : cascade **config explicite de la requête > credential utilisateur persistant chiffré** (AES-256-GCM, clé dérivée HKDF d'une clé maître, sel par utilisateur — révisée par la décision 25 : plusieurs configurations nommées par utilisateur, la cascade lit l'**active**, sel par ligne) **> fallback serveur `AI_*`**, ce dernier seul **compté** sous un quota quotidien par utilisateur (`users.ai_daily_call_quota`, NULL = défaut, 0 = illimité, **sans CHECK SQL**, jamais écrit par une route) ; réservation atomique avant l'appel, remboursement si le provider échoue, un flux qui a produit du contenu **reste compté**.
- Conséquences : `app/core/ai/` reste stateless (la cascade vit dans `ai_credentials.service.effective_config`) ; seul `app/core/ai/` importe langchain/langgraph/langfuse, seul `app/core/crypto.py` importe `cryptography` ; une clé refusée par le provider est un **400** (401 réservé au JWT) ; la clé n'apparaît dans aucun schéma de réponse.
- Code : `app/core/ai/`, `app/ai_credentials/`, `app/models/ai_daily_usage.py`.

## 6. Liens de partage : capability URL, expiration obligatoire, 404 uniforme (avant 2026-09)

- Décision : token opaque 256 bits stocké **en clair** (recopiable à tout moment), `expires_at` obligatoire (270 jours), révocation soft ; la visibilité `draft` **suspend** les liens sans les supprimer ; toute erreur du régime public est un **404 « Cours introuvable »**, jamais 401/403/410 (aucun oracle) ; le token voyage en `?token=`.
- Conséquences : validité vérifiée à chaque accès en Python ; les routes `/api/v1/public/*` ne portent aucune dépendance JWT ; le front n'y attache jamais de Bearer, même pour un prof connecté.
- Code : `app/share_links/`, `app/public/service.py`, front `app.config.ts` (`customUrlValidation`).

## 5. Un bloc pointeur meurt avec sa cible (avant 2026-09)

- Décision : un bloc `document` pointe une ressource et un bloc `module` un module par une **colonne** FK nullable en `ON DELETE CASCADE` ; supprimer la cible supprime les blocs pointeurs.
- Conséquences : le front recharge le détail du cours après une suppression de ressource/module ; les CHECKs de cohérence limitent `resource_id` aux blocs `document` et `module_id` aux blocs `module`.
- Code : `app/models/block.py`.

## 4. Modules interactifs : code en base, bac à sable sans réseau (avant 2026-09)

- Contexte : le cadrage §5.5 prévoyait un bundle `.zip` sur S3 avec versionnage par clé et des CDN autorisés.
- Décision : un module = **code HTML/CSS/JS stocké en base** et édité dans l'app ; exécution en **iframe sandbox à origine opaque** (`sandbox` statique **sans** `allow-same-origin`) avec une **CSP dans le srcdoc** : `default-src 'none'`, inline et `data:`/`blob:` seuls autorisés, `'unsafe-eval'` toléré (grapheurs), `form-action 'none'` — **aucun réseau sortant**.
- Conséquences : modules self-contained (aucun CDN, aucune police distante — les librairies du catalogue sont inlinées par le runtime, décision 30) ; le prompt `MODULE_RUNTIME` du back est le miroir du contrat de `module-document.ts` — toute évolution de l'un se reporte dans l'autre ; une future CSP d'en-tête posée par l'infra devra tolérer `'unsafe-eval'` ; le srcdoc est posé impérativement (jamais `[srcdoc]`, le sanitizer Angular striperait les scripts).
- Code : `app/modules/`, front `shared/module-runner/module-document.ts`.

## 3. Pas de binaire par le backend — sauf l'export/import de cours (avant 2026-09)

- Contexte : cible Raspberry Pi (RAM, bande passante) ; les uploads sont directs navigateur → S3 par URL présignée.
- Décision : l'API ne transporte jamais de binaire, **à une exception près** : l'archive `.zip` d'export/import est assemblée et parsée par l'API (volumes bornés par `TRANSFER_MAX_ZIP_BYTES`, assemblage dans un fichier temporaire spoolé, jamais une archive entière en RAM).
- Conséquences : seules deux méthodes de bytes dans `storage.py` (`read_object_into`, `put_object`) ; ordre transactionnel de l'import : inserts sans commit → put S3 → commit (au pire un orphelin bucket, jamais une référence DB vers un objet absent) ; la suppression purge S3 **après** commit.
- Code : `app/course_transfer/`, `app/core/storage.py`.

## 2. Une seule extension Postgres, pas de pgvector (avant 2026-09)

- Décision : aucune extension Postgres, à une exception actée pour la recherche : contrib `unaccent` + configuration `french_unaccent` (stemming + insensibilité aux accents). Pas de pgvector ; si la vectorisation se fait, ce sera probablement ChromaDB.
- Conséquences : toute autre extension reste à arbitrer explicitement ; les vecteurs FTS sont maintenus par triggers, jamais par l'ORM, et n'indexent jamais `expected_answer`.
- Code : migration FTS, `app/search/`.

## 1. Resource server pur, IdP remplaçable (avant 2026-09)

- Contexte : le cahier des charges exige de pouvoir changer d'IdP en ne touchant qu'un module par application.
- Décision : la SPA porte tout le flow OIDC (Authorization Code + PKCE vers Zitadel) ; l'API n'émet jamais de token, ne stocke aucune identité et valide le JWT de chaque requête ; la logique IdP est **confinée** dans `app/core/auth.py` (back) et `AuthService` (front, seul importeur d'`angular-oauth2-oidc`).
- Conséquences : `OIDC_AUDIENCE` = client id du front ; Zitadel doit émettre des JWT access tokens ; `get_current_user` ne touche jamais la base (la résolution `sub → users` vit dans `app/users/`) ; token invalide → 401 + `WWW-Authenticate`, IdP injoignable → 503, jamais 500, jamais le token dans les logs.
- Code : `app/core/auth.py`, front `src/app/core/auth/`.
